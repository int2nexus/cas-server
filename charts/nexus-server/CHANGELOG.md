# nexus-server 차트 변경 이력

각 `##` 섹션이 그대로 해당 버전의 **GitHub Release 본문**이 됩니다
(`scripts/extract-release-notes.sh` 가 발췌 → chart-releaser 가 릴리스 본문으로 사용).

`Chart.yaml` 의 `version` 을 올릴 때 이 파일 맨 위에 섹션을 함께 추가하세요.
섹션이 없으면 릴리스 워크플로가 실패합니다.

해당 사항이 없는 항목도 **"없음"이라고 적습니다** — 도입하는 쪽이 *없었다* 와 *안 썼다* 를
구별할 수 있어야 합니다.

```markdown
## <version>

image: `int2jieun/nexus-server:<tag>` (변경 없음이면 그렇게 적기)

**동작 변경** — 없음
**마이그레이션** — 없음
**설정 키** — 없음
```

### 선택 라벨

세 항목은 **최소**입니다. 더 알려야 할 게 있으면 아래 라벨을 같은 모양(`**라벨** — 내용`)으로
덧붙입니다. 같은 라벨을 여러 번 써서 묶어도 됩니다.

- `**호환성**` — 요구하는 최소 appVersion·이미지 태그, 맞지 않을 때 벌어지는 일
- `**운영 조치**` — 이 버전 때문에 되돌리거나 새로 해야 하는 운영 작업
- `**주의**` — 버전과 무관하게 지켜야 하는 제약을 이 릴리스에서 처음 문서화한 경우

라벨 볼드 안에 수식어까지 넣지 마세요 — `**동작 변경 — 차트**` 가 아니라
`**동작 변경** — 차트` 입니다. 도입하는 쪽이 라벨을 훑어 찾기 때문에 라벨 자체가
고정된 문자열이어야 합니다.

### 마이그레이션 항목 쓰는 법

nexus-server 는 마이그레이션이 바이너리에 임베드되어 **기동 시 자동 적용**되고, 기동이
마이그레이션 성공에 게이트됩니다(`/_internal/health` 가 200이면 적용 완료). 별도 Job 이
없어서 도입하는 쪽에는 릴리스 노트가 유일한 사전 정보입니다. 스키마가 바뀌는 버전이면
아래 세 줄을 함께 적습니다.

- **영향받는 테이블** — 이름을 나열합니다
- **예상 소요시간** — 행 수 기준으로 적습니다. 마이그레이션이 끝날 때까지 Pod 가 Ready 되지
  않으므로 이 시간이 곧 점검창입니다
- **롤백** — 둘 중 해당하는 쪽을 명시합니다
  - **추가만 하는 변경**(테이블·컬럼 추가): 이전 이미지가 새 스키마에서 그대로 기동하므로
    `helm rollback <release> <revision>` 으로 안전하게 되돌아갑니다. "롤백 안전"이라고 적습니다.
  - **파괴적 변경**(삭제·타입 변경·NOT NULL 추가) 또는 **되돌리는 마이그레이션이 없는 경우**:
    **"이 버전은 DB 마이그레이션을 포함하며 이전 버전으로 롤백할 수 없습니다"** 를 그대로
    적습니다. `helm rollback` 은 차트와 이미지만 되돌리고 **이미 적용된 스키마는 되돌리지
    않으므로**, 구버전 이미지가 새 스키마에서 기동하지 못할 수 있습니다. 되돌리려면
    업그레이드 전에 떠 둔 DB 스냅샷(`pg_dump`)을 복원하는 방법밖에 없다는 점을 함께 씁니다.

## 0.3.1

image: `int2jieun/nexus-server:0.1.4`

**동작 변경** — **`serviceAccount.automountToken`이 이제 실제로 적용됩니다.** 지금까지 이 값은 `templates/serviceaccount.yaml`에만 렌더됐는데, 그 파일은 `serviceAccount.create: true`일 때만 만들어져 **기본값(`create: false`) 설치에서는 아무 효과가 없었습니다** — 파드는 네임스페이스의 `default` ServiceAccount를 쓰고, 그 ServiceAccount 자체가 `automountServiceAccountToken: false`로 설정되어 있지 않은 한 그 토큰이 그대로 마운트됐습니다(대부분의 클러스터가 이 기본 상태이지만, `default` ServiceAccount를 직접 잠가 둔 클러스터라면 예전에도 토큰이 없었을 수 있습니다). `values.yaml`은 `false`라고 문서화하고 있었으므로, 표준 클러스터라면 이는 그 문서화와 반대되는 동작이었습니다. `0.3.1`부터는 Deployment podSpec에도 `create` 여부와 무관하게 직접 렌더됩니다. Pod에 명시된 값은 항상 ServiceAccount 쪽 설정보다 우선합니다(쿠버네티스 우선순위).

**주의** — **기본 설치의 동작이 뒤집힙니다: "토큰 마운트됨" → "토큰 마운트 안 됨".** `0.3.0` 이하에서는 기본 설치가 (버그로) `default` ServiceAccount의 토큰을 그대로 마운트했습니다. `0.3.1`부터는 문서대로 마운트되지 않습니다. nexus-server 자체는 쿠버네티스 API를 부르지 않아 영향이 없지만, 그 파드의 토큰에 기대던 디버그 컨테이너·사이드카·서비스 메시가 있다면 토큰을 잃습니다 — 필요하면 `--set serviceAccount.automountToken=true`로 되돌리세요. 값이 바뀌는 순간 파드 스펙이 바뀌므로 **롤링 재시작이 한 번 일어납니다.**

**동작 변경** — **`delete_cas` 기본값이 "삭제"에서 "보존"으로 바뀝니다.** `DELETE /datasets/{id}/versions/{v}`와 `DELETE /samples/{sample_id}` 둘 다 대상입니다. 지금까지는 파라미터를 생략하면 미참조 이미지·썸네일 바이트가 CAS에서 **영구히** 삭제됐습니다. `0.1.4`부터는 생략하면 보존되고, 예전처럼 지우려면 **`delete_cas=true`를 명시적으로 줘야 합니다.**

바꾼 이유는 실패 방향의 비대칭입니다 — 잘못된 `false`는 미참조 파일이 남는 것뿐이라 되돌릴 수 있는 스토리지 비용이지만, 잘못된 `true`는 바이트를 되돌릴 수 없이 파괴합니다. 기본값은 되돌릴 수 있는 쪽으로 두는 것이 안전합니다. **이 릴리스에서 가장 영향이 큰 변경입니다** — 삭제 후 CAS 용량이 자동으로 정리되는 것에 의존해 온 운영이라면, 업그레이드 후 그 정리가 멈춥니다(파일이 안 지워질 뿐 삭제 요청 자체는 그대로 성공합니다). 예전 동작이 필요한 호출부는 전부 `delete_cas=true`를 명시하도록 고쳐야 합니다.

**동작 변경** — **readiness 응답에 근거가 실립니다.** `GET /_internal/health`가 성공 시 `{"status":"ok","db":true}`, 실패 시 `{"status":"error","db":false}`(503)를 반환합니다. 지금까지 성공 응답은 `{"status":"ok"}`뿐이라 DB를 실제로 확인하지 않던 구버전 빌드와 구분할 수 없었습니다. 프로브는 상태 코드만 읽으므로 **프로브 동작 자체는 바뀌지 않습니다** — 응답 본문을 직접 파싱하는 스크립트가 있을 때만 영향이 있습니다.

**동작 변경** — **기동 마이그레이션 로그가 적용 건수를 알려줍니다.** 형식이 `마이그레이션 완료 applied=<건수> elapsed_ms=<소요>`로 바뀝니다. `replicaCount: 1`이면 `applied`가 0보다 큰 기동만 실제 스키마 작업을 측정한 것입니다 — 적용할 것이 없는 기동도 `elapsed_ms`는 찍힙니다(버전 확인 자체의 비용입니다). `applied`를 보지 않고 `elapsed_ms`만 스키마 반영 시간으로 읽으면 착오가 생기는데, 이 필드가 그 착오를 막기 위한 것입니다. **`replicaCount > 1`이면 이 판단이 그대로 맞지 않을 수 있습니다** — `applied`는 이 프로세스의 마이그레이션 실행 동안 DB 전체에 걸린 델타이고, 여러 파드가 동시에 뜨면 sqlx가 advisory lock으로 순서를 정렬하기 때문에, 자신은 아무것도 적용하지 않은 파드도 0이 아닌 `applied`를 보고할 수 있습니다.

**동작 변경** — **annotation 왕복 엔드포인트 추가**(`GET /datasets/{id}/versions/{v}/samples/{sid}/annotations`). 같은 경로의 기존 `PUT`이 `annotation_data` 안에 받는 것과 정확히 같은 모양을 그대로 돌려줍니다 — 평탄화된 샘플 응답을 거치지 않고 annotation을 받아서 고쳐서 그대로 다시 저장할 수 있습니다. Python SDK `int2nexus-sdk 0.1.5`에 `ds.get_annotation()`/`ds.save_annotation()`이 함께 추가됐습니다. **`PUT`은 그 버전의 인스턴스를 병합이 아니라 통째로 교체합니다** — 받은 것 일부만 고쳐 보내면 나머지가 사라집니다.

**동작 변경(주의)** — **같은 경로의 `PUT` 응답이 `204 No Content`에서 `200 OK` + 본문으로 바뀝니다.** 본문은 `{"instances": n, "skipped": n, "skipped_reasons": {"missing_label": n, "not_an_object": n, "group_not_an_array": n}}` 형태입니다. 서버는 형식이 어긋난 인스턴스(`label` 필드가 없는 원소, object가 아닌 원소, 값이 배열이 아닌 그룹)를 버리는데, 지금까지는 버리고도 `204`를 돌려줘 클라이언트가 유실을 성공으로 읽었습니다. `PUT`이 통째 교체라 버려진 원소는 "안 들어간" 것이 아니라 **원래 있던 인스턴스가 지워진** 것이므로, 그 수를 응답에 싣습니다. `skipped`가 0이 아니면 그만큼 유실이 일어난 것입니다. **`2xx`로 성공을 판정하는 클라이언트는 영향이 없지만, 상태 코드가 `204`인지로 판정하는 클라이언트는 고쳐야 합니다.** SDK는 양쪽으로 관대합니다 — `0.1.5`는 구 서버의 빈 본문에서 예외를 던지지 않고, `skipped`가 0이 아니면 `RuntimeWarning`을 냅니다.

**마이그레이션** — 없음. 새 테이블도 컬럼도 없습니다. 스키마 기준으로는 `helm rollback`이 안전합니다 — 다만 `0.3.0`으로 롤백하면 이미지도 `0.1.3`으로 함께 되돌아가므로, 위에서 바뀐 `delete_cas` 기본값도 함께 되돌아갑니다. 즉 롤백 후에는 `delete_cas`를 생략한 삭제 요청이 다시 **예전처럼 미참조 CAS 객체를 삭제**합니다 — 롤백이 스키마를 해치지는 않지만 이 동작 변경까지 되돌린다는 점은 알고 있어야 합니다.

**설정 키** — 없음. `automountToken`은 이미 있던 키이고 이번에는 배선만 고쳤습니다.

**호환성** — appVersion **`0.1.4`** 필요. 프로브 경로는 `0.3.0`과 동일해 구 이미지에서도 파드가 깨지지는 않지만, 위 `delete_cas` 기본값 변경·readiness 근거·마이그레이션 로그 건수·annotation 왕복 엔드포인트는 구 이미지에는 **존재하지 않습니다.** annotation 왕복 메서드(`ds.get_annotation()`/`ds.save_annotation()`)를 쓰려면 SDK **`0.1.5`** 이상이 필요합니다 — 구 SDK에는 그 메서드 자체가 없습니다.

## 0.3.0

image: `int2jieun/nexus-server:0.1.3`

설정 키가 늘어 minor 를 올렸습니다(0.2.1 → 0.3.0). **아무것도 하지 않으면 동작이 그대로입니다** — 새 키를 비워두면 기능이 켜지지 않습니다.

**동작 변경** — **superuser 계정 추가**(선택). 비밀번호를 잊어 로그인할 수 없는 계정을 풀어주고, dataset 소유자를 지정하는 단일 관리 계정입니다. 지금까지 이 셋은 DB 를 손으로 고쳐야 했습니다. 능력은 둘뿐입니다 — `POST /api/v1/admin/users/password-reset`(임시 비밀번호를 생성해 **응답에 한 번만** 돌려줍니다. 어디에도 저장하지 않습니다)과 `PUT /api/v1/admin/datasets/{dataset_id}/owner`(양도와 인수가 같은 연산입니다). 사용자 목록·계정 비활성화·감사 로그는 없습니다.

권한은 DB 컬럼이 아니라 **설정값 비교**입니다(`is_superuser` 컬럼이 없습니다). 그래서 권한이 토큰에 박히지 않고, **이메일을 바꿔 재배포하면 즉시 회수됩니다** — 토큰을 무효화할 수 없는 이 서버에서 유일한 예외입니다. 반대로 **비밀번호를 재설정해도 그 사용자의 기존 토큰은 만료까지(최대 24시간) 유효합니다.** "잊어버림"을 푸는 도구지 "탈취 즉시 차단"이 아닙니다.

**동작 변경** — **superuser 이메일로는 가입할 수 없고(409), superuser 는 자기 계정을 지울 수 없습니다(403).** 권한이 "토큰의 이메일 == 설정값"이라 그 주소의 계정을 쥔 사람이 곧 superuser 이기 때문입니다. 삭제가 하드 삭제이고 회원가입이 공개인 이 서버에서, 이 두 가드가 없으면 계정이 사라진 창에 아무나 그 주소로 가입해 최고 권한을 가져갈 수 있습니다. 가입 거부 응답은 이미 등록된 이메일과 **구분되지 않습니다**(같은 409, 같은 본문).

**설정 키** — **`auth.superuserEmail`**(values, 기본 `""`)과 **`NEXUS__AUTH__SUPERUSER_PASSWORD`**(시크릿, 8자 이상). 둘 다 비우면 기능이 꺼지고 `/api/v1/admin/*` 는 누구에게나 403 입니다.

**주의** — **한쪽만 채우면 서버가 기동에 실패합니다.** 조용히 꺼지지 않습니다(CVAT 과 다른 점입니다). 운영자가 켰다고 믿는데 실제로는 꺼져 있는 상태가 가장 나쁘고, 그 사실이 정작 필요한 순간에야 드러나기 때문에 의도한 동작입니다. **차트는 이 짝을 검사할 수 없습니다** — 비밀번호는 Secret 에서 `envFrom` 으로 들어와 템플릿에 보이지 않습니다. `helm upgrade` 는 조용히 성공하고 **Pod 가 CrashLoop 로 드러나며**, 어느 쪽이 빠졌는지는 `kubectl logs` 에 적힙니다. **끌 때도 두 곳을 함께 비우세요** — values 만 지우고 Secret 에 비밀번호를 남기면 역시 기동에 실패합니다.

**주의** — **시크릿의 비밀번호는 최초 계정 생성 때만 쓰입니다.** 서버가 기동 시 그 계정이 없으면 만들고(그래야 그 주소를 아무도 선점할 수 없습니다), 이미 있으면 **비밀번호를 덮지 않습니다** — 운영자가 API 로 바꾼 값이 파드 재시작마다 되돌아가면 안 되기 때문입니다. 나중에 이 env 를 바꿔도 로그인 비밀번호는 바뀌지 않습니다. 잊었다면 그 계정을 지우고 다시 기동해야 합니다.

**주의** — **이미 운영 중인 클러스터에서 켤 때는 그 주소가 이미 가입되어 있지 않은지 확인하세요.** 기동 시 그 이메일의 계정이 이미 있으면 서버는 그것을 **그대로 채택하고 비밀번호를 덮지 않습니다.** 즉 누군가 그 주소로 먼저 가입해 두었다면 그 사람이 superuser 가 됩니다. 선점 방지는 "서버가 먼저 만든다"로 이뤄지므로, 가입을 받기 전에 켜 두는 것이 안전합니다. 채택이 일어나면 기동 로그에 `warn` 으로 남습니다(새로 만들면 `info`).

**마이그레이션** — 없음. 새 테이블도 컬럼도 없습니다. 따라서 `helm rollback` 으로 이전 차트·이미지로 되돌아가는 것이 안전합니다.

**호환성** — **appVersion 0.1.3 이상이 필요합니다.** 그 이전 이미지는 `NEXUS__AUTH__*` 를 무시하므로 기동이 깨지지는 않지만 기능도 켜지지 않고, `/api/v1/admin/*` 는 404 입니다. `auth.superuserEmail` 을 비워두면 env 자체가 렌더되지 않아 어떤 이미지에서도 안전합니다.

**운영 조치** — **주인 없는 dataset 을 정리하려면 이 버전이 필요합니다.** `owner_user_id` 가 NULL 인 dataset 은 잠긴 것이 아니라 **인증된 누구나 쓸 수 있는** 상태입니다(소유자 게이트가 NULL 을 통과시킵니다). 계정을 하드 삭제하면 그 사람이 만든 dataset 이 전부 이 상태가 됩니다 — 필요 시 `GET /datasets` 의 `owner_user_id` 로 찾아 `PUT /api/v1/admin/datasets/{dataset_id}/owner` 로 다른 주인을 지정하세요.

**동작 변경** — **SDK `nx.upload` 에 `overwrite` 옵션이 생겼습니다**(서버·차트는 영향 없음, SDK 전용). 같은 CAS key 에 다른 내용이 이미 있으면 기본은 여전히 충돌 에러이고, `overwrite=True` 를 주면 대신 덮어씁니다 — 이때 썸네일도 새 내용으로 함께 다시 만듭니다(안 그러면 옛 썸네일이 새 이미지에 남습니다). 같은 내용이면 옵션과 무관하게 그대로 건너뜁니다.

**호환성** — **SDK 0.1.4 이상이 필요합니다.** 그 이전 SDK 로 `overwrite=True` 를 주면 `TypeError` 로 즉시 실패합니다(서버는 관여하지 않습니다). 옵션을 안 쓰면 구 SDK 로도 그대로 동작합니다.

**동작 변경** — **프로브가 셋으로 갈립니다.** 지금까지는 liveness·readiness 가 둘 다
`/_internal/health` 를 봤고, 그 핸들러는 **의존성을 조회하지 않고 무조건 200 을
돌려줬습니다** — readiness 가 아무것도 판정하지 않는 상태였습니다. 0.3.0 부터
`/_internal/live`(조회 없음)가 startup·liveness 를, `/_internal/health`(DB ping)가
readiness 를 맡습니다. liveness 가 DB 를 보면 DB failover(보통 30~120초)에 파드가
kill 되는데 재시작으로는 의존성이 복구되지 않아, 중단이 원래 장애보다 길어집니다.

**호환성** — 프로브 경로도 **appVersion 0.1.3 이상**을 요구합니다. `Chart.yaml` 의 appVersion 과 `values.yaml` 의 `image.tag` 를 모두 `0.1.3` 으로 맞춰 두었으므로 평소대로 올리시면 따로 하실 일은 없습니다. `--set image.tag` 로 **의도적으로 `0.1.2` 이하를 쓰시는 경우에만** 주의가 필요합니다 — startupProbe·livenessProbe 가 보는 `/_internal/live` 가 그 이미지에는 없어 404 가 프로브 실패로 계산되고, 파드가 Ready 에 이르지 못한 채 재시작을 반복합니다. 그때는 `startupProbe.enabled: false` 와 `livenessProbe.httpGet.path: /_internal/health` 를 함께 지정해 이전 동작으로 되돌리십시오.

**동작 변경** — **startupProbe 가 생겼습니다**(`periodSeconds 10 × failureThreshold 60`
= 기동 예산 600초). 서버는 마이그레이션·superuser 부트스트랩·CVAT 정리를 **전부 끝낸 뒤에**
포트를 엽니다. 그 구간의 프로브는 "200 이 아닌 응답"이 아니라 **connection refused** 를
받으므로, 예산이 없으면 스키마를 바꾸는 릴리스에서 kill → 재기동 → 마이그레이션 재시작이
반복됩니다. 실제 마이그레이션 소요는 기동 로그의 `마이그레이션 완료 elapsed_ms=…` 줄로
확인하실 수 있습니다(0.1.3 에서 함께 추가).

**수정** — **`serviceAccount` 가 실제로 배선됩니다.** 지금까지 `values.yaml` 에 블록은
있었지만 템플릿이 그 값을 참조하지 않아, 설정하셔도 **조용히 아무 일도 일어나지
않았습니다.** PodSecurity/NetworkPolicy 를 ServiceAccount 기준으로 거는 경우 통제를
걸었다고 믿는데 실제로는 안 걸린 상태였습니다. `create: true` 면 차트가 만들고,
`false` 면 기존 것을 씁니다(`name` 이 비면 `default`). 토큰은 기본으로 마운트하지
않습니다(`automountToken: false`) — 파드가 쿠버네티스 API 를 부르지 않기 때문입니다.

**설정 키** — **`jwt.ttlHours`**(비우면 서버 기본 24시간, 범위 1~8760).
이 서버는 **토큰을 무효화할 수 없으므로** 이 값이 곧 탈취·계정삭제·비밀번호변경의
노출 상한입니다. 범위를 벗어난 값을 주면 **기동에 실패합니다**(DB 연결보다 먼저 검사).
"설정 안 함"은 빈 문자열뿐입니다 — `0`을 주면 (빈 값과 달리) 그대로 서버에 전달되고,
범위 밖이라 기동이 실패합니다. 조용히 기본 24시간으로 되돌아가지 않습니다.

**설정 키** — **`auth.registrationEnabled`**(기본 `true`). `false` 로 하면
`POST /api/v1/auth/register` 만 403 이 되고 로그인·갱신·기존 계정 동작은 그대로입니다.
다만 **끄기 전에 필요한 계정을 먼저 만들어 두십시오** — 끈 뒤에는 superuser 도
새 계정을 만들 수 없습니다(계정 생성 경로가 register 하나뿐입니다).

**설정 키** — **`auth.docsEnabled`**(기본 `true`). `false` 로 하면
`/api-docs/openapi.json`·`/swagger-ui`·`/swagger-ui/` 세 경로가 **404** 가 됩니다
(403 이 아닙니다 — "있지만 막혔다"보다 "없다"가 덜 알려줍니다).

**설정 키** — **`waitForPostgres`**(기본 **꺼짐**). DB 가 뜨기 전에 기동하면 커넥션 풀
생성에서 즉시 실패해 CrashLoopBackOff 에 빠집니다. 기본을 끈 이유는 이 차트가 DB 주소를
Secret 의 `NEXUS__DATABASE__URL` 로만 받기 때문입니다 — 여기 host/port 를 적으면 같은
정보가 두 곳에 생겨 어긋날 수 있어, 켜는 쪽이 그 중복을 감수하겠다고 선택하는 구조로
두었습니다. startupProbe 600초만으로도 대부분의 경우 충분합니다.

**운영 조치** — **CVAT 편집을 쓰는 데이터셋이라면 업그레이드 후 크기 보정을 한 번 돌리세요.** 위 동작 변경은 **앞으로 등록될** 샘플에만 해당합니다. 이전에 `0`으로 적재된 기존 샘플은 여전히 세션 생성을 통과한 뒤 export에서 조용히 빠지며, 그것을 고치는 도구가 SDK 0.1.3의 `ds.backfill_dims()`입니다.

```python
ds = nx.load_or_create("<dataset>", version="<version>")
report = ds.backfill_dims(dry_run=True)   # 대상 규모와 실제 측정 가능 건수만 확인
report = ds.backfill_dims(workers=8)      # 적용
```

**주의** — **이 엔드포인트는 sealed 버전에 속한 샘플의 `meta`도 채웁니다.** Seal 이후 모든 변경이 차단된다는 원칙의 예외처럼 보이지만, `samples.meta`는 애초에 seal의 대상이 아닙니다 — seal이 CAS에 박제하고 해시로 고정하는 것은 annotation 스냅샷이고, sealed 버전의 `meta` 조회는 언제나 살아 있는 행을 읽어 왔습니다. 게다가 이 경로는 빈칸을 채우는 것만 가능해 기록된 값을 지울 수 없습니다. `0`은 측정된 값이 아니라 구 SDK가 자리를 채우려고 넣은 값이므로, 그대로 얼려두는 것은 재현성을 지키는 일이 아니라 결함을 보존하는 일이 됩니다. 이 성질을 이번 릴리스에서 처음 문서화합니다.

SDK 0.1.2부터 예외를 던집니다.

③ **`POST /api/v1/upload/presign`이 제거되었습니다** — 호출하면 404. 요청한 bucket/key를 그대로 서버 자격증명으로 서명해 줘서, 인증된 사용자면 누구나 남의 sealed manifest를 덮어쓸 수 있었습니다. 업로드는 SDK가 CAS 자격증명으로 직접 서명합니다(`nx.upload`) — **SDK는 이 엔드포인트를 쓴 적이 없어 SDK 사용자는 영향이 없습니다.** 직접 호출하는 자체 코드가 있는지만 확인하세요.

④ **CAS bucket/key에 문법 제약이 생겼습니다.** key에 `%`(퍼센트 인코딩)·선행 `/`·`..`·`//`·제어문자를 쓸 수 없고, bucket은 S3 규칙(소문자·숫자·`-`·`.`, 3~63자)을 따라야 합니다. 또 `thumb/`·`manifests/`·`annotations/`로 시작하는 key는 asset으로 등록할 수 없습니다(nexus가 관리하는 시스템 객체 영역이라, 등록을 허용하면 샘플 삭제만으로 남의 썸네일·sealed manifest를 지울 수 있었습니다). **위반 시 ingest가 400**입니다. **기존 데이터의 조회·seal은 영향받지 않습니다** — 제약은 신규 등록에만 걸립니다. 다만 그런 key를 가진 기존 CAS 객체는 삭제 시 회수되지 않고 남습니다(삭제 자체는 정상 성공).

**동작 변경** — **`POST /api/v1/auth/refresh` 추가**(파괴적 아님). 아직 유효한 토큰을 새 24시간 토큰으로 바꿉니다. 응답은 로그인과 같은 모양이라 그대로 바꿔 끼우면 됩니다. **만료된 뒤에는 갱신할 수 없으므로**(401) 클라이언트는 만료를 기다리지 말고 미리 불러야 합니다 — 401을 받고 나서는 이미 늦어 다시 로그인해야 합니다. 비밀번호를 받지 않으므로 자격증명을 보관하면 안 되는 프론트엔드가 대상입니다. 인증 경로에서 유일하게 DB를 조회하는데, 안 그러면 삭제된 계정이 갱신을 반복해 영구히 접근을 유지할 수 있기 때문입니다.

**동작 변경** — **`POST /api/v1/auth/password`(비밀번호 변경)·`DELETE /api/v1/auth/account`(계정 삭제) 추가**(파괴적 아님). 기존 동작을 바꾸지는 않지만, 두 가지를 알고 써야 합니다.

- **토큰은 발급 후 만료(최대 24시간)까지 무효화할 수 없습니다.** 서버가 요청마다 토큰을 검증할 때 DB를 조회하지 않기 때문입니다(대량 적재 시 커넥션 경합을 피하려는 선택). 따라서 **비밀번호를 바꾸거나 계정을 삭제해도 이미 발급된 토큰은 만료 시점까지 유효합니다.** 자격증명 유출에 대응해 비밀번호를 바꾸는 경우, 유출된 토큰이 최대 24시간 더 살아 있다는 뜻입니다. 즉시 차단이 필요하면 `NEXUS__JWT__SECRET`을 교체해야 하고, 그 경우 **모든 사용자가 재로그인**합니다.
- **계정 삭제는 그 계정이 소유한 dataset을 지우지 않고 소유자만 해제합니다.** 삭제 응답의 `released_datasets`가 해제된 개수입니다. 한 사람의 탈퇴로 팀이 쓰던 학습 데이터가 사라지는 편이 더 위험하다는 판단입니다. 대신 그 dataset은 `owner_user_id`가 NULL이 되어 **위 ②의 보호를 받지 못합니다** — 인증된 누구나 수정·삭제할 수 있고, 마지막 version을 삭제하면 dataset도 함께 사라집니다. CAS에 있는 원본 객체는 삭제 요청에 `delete_cas`를 지정한 경우에만 CAS로 삭제 요청이 가고, 그때도 실제 정리는 CAS 쪽 GC가 수행합니다.

**마이그레이션** — 포함. 서버 이미지 0.1.1에 annotation session 테이블 추가가 들어갑니다.

- 영향받는 테이블: `annotation_sessions`, `annotation_session_frames` (신규 생성)
- 예상 소요시간: 테이블 생성만이라 행 수와 무관하게 수 초
- 롤백: **스키마는 안전합니다.** 추가만 하는 변경이라 이전 이미지가 새 스키마에서 그대로
  기동합니다. 다만 **되돌리면 이 릴리스의 보안 변경도 함께 원복됩니다** — ①②의 인증·소유권
  검사가 사라지고 ③의 `upload/presign`이 되살아납니다. 장애 대응으로 이미지를 0.1.0 으로
  내리는 경우, 그 구간에는 조회 API가 다시 무인증으로 열린다는 점을 알고 내려야 합니다.

**설정 키** — `cvat.baseUrl`, `cvat.user`, `cvat.organization`, `cvat.projectNamePrefix`, `cvat.segmentSize`, `cvat.maxSessionSamples`, `cvat.staleCreatingSecs` 추가. **전부 선택입니다.** `projectNamePrefix`만 `nexus`이고 나머지는 비어 있습니다 — 비워두면 해당 env가 렌더되지 않아 서버 기본값(`segmentSize` 0, `maxSessionSamples` 2000, `staleCreatingSecs` 1800)이 적용됩니다.

**설정 키** — `service.targetPort`와 두 프로브의 `httpGet.port`가 숫자 `8090`에서 **컨테이너 포트 이름 `http`**로 바뀌었습니다. 기본값 배포에서는 렌더 결과가 동일해 영향이 없습니다. 이제 `server.port` 하나만 바꾸면 컨테이너·앱·Service·프로브가 모두 따라갑니다 — 전에는 `server.port`만 바꾸면 프로브가 옛 포트를 찔러 Pod가 Ready가 되지 않았습니다. `values-*.yaml`에서 이 세 값을 숫자로 override하고 있었다면 그대로 동작하지만, `server.port`와 어긋나지 않는지 확인하세요.

**호환성** — CVAT 연동에는 **appVersion 0.1.1 이상**이 필요합니다. 그 이전 이미지는 `cvat` 설정 자체를 모릅니다. 다만 `NEXUS__CVAT__*` env를 줘도 **기동이 깨지지는 않습니다** — 모르는 설정 섹션은 무시되고 CVAT 기능만 없는 상태로 정상 기동합니다(실측 확인). 

**호환성** — `ingest.batchItemConcurrency`는 이야기가 다릅니다. 그 필드는 구 이미지에도 **존재하되** 하위 필드에 serde 기본값이 없던 시기가 있어, 일부만 주입하면 역직렬화가 실패해 기동이 깨집니다. `values.yaml`의 해당 주석을 참고하세요.

**호환성** — **Python SDK는 0.1.2 이상을 권장합니다.** 0.1.0/0.1.1도 동작은 합니다(로그인 시 세션 헤더에 토큰을 붙여 모든 요청에 실어 보내므로 위 ①에 걸리지 않습니다). 올려야 하는 이유는 ②입니다 — 구 SDK는 소유권 거부를 예외로 올리지 않아 적재 실패가 조용히 지나갑니다. SDK 0.1.2를 구버전 서버에 써도 전면 실패하지는 않고, 계정 API와 annotation session 기능만 404가 됩니다.

0.1.2는 토큰 만료도 스스로 처리합니다 — 만료 5분 전부터 위 `refresh`로 미리 갱신하고, 그래도 만료된 채 호출하면 401을 받아 자동으로 다시 로그인한 뒤 재시도합니다. 오래 도는 적재 스크립트나 며칠 열어둔 노트북을 재시작할 필요가 없어집니다. 구버전 서버에 붙으면 `refresh`가 404이므로 한 번만 확인하고 재로그인 방식으로만 동작합니다.

**운영 조치** — **이미지 태그를 따로 지정하지 마세요.** 차트와 이미지는 함께 검증해서 짝으로 내보냅니다. 옵션 없이 올리면 이 차트가 정한 조합(`int2jieun/nexus-server:0.1.1`)이 그대로 설치됩니다.

```bash
helm repo update
helm upgrade --install nexus-server int2nexus/nexus-server -n <namespace> \
  --set cas.baseUrl=<CAS 주소>          # 환경별 값만 지정
```

`--set image.tag=...`로 덮으면 차트가 기대하는 서버 동작과 실제 이미지가 어긋날 수 있습니다. 이 버전은 특히 **차트 쪽 변경(CVAT env 조건부 주입, named port)과 서버 쪽 변경(인증·소유권)이 함께 맞물려** 있습니다. 태그를 지정해야 하는 경우는 롤백처럼 의도적으로 이전 이미지를 쓸 때뿐이고, 그때는 아래 `**호환성**` 항목을 먼저 확인하세요.

**운영 조치** — **업그레이드 전에 무인증으로 nexus를 호출하는 클라이언트가 있는지 점검하세요.** 대시보드, 크론 스크립트, `curl` 기반 헬스체크가 대상입니다. 토큰 없이 조회하던 것이 하나라도 있으면 업그레이드 직후 401로 죽습니다. 프론트는 401(재로그인)과 403(권한 없음)을 구분해 처리해야 합니다 — 둘을 같이 다루면 권한 문제에서 무한 재로그인 루프가 납니다.

**운영 조치** — **적재 경로의 Python SDK를 0.1.2 이상으로 올리세요.** 위 ②가 이 릴리스에서
가장 조용한 실패입니다. 구 SDK는 소유권 거부(403)를 예외로 올리지 않고 종료코드 0으로 끝나서,
적재 CI·크론이 **아무것도 넣지 않은 채 성공으로 표시됩니다.** 로그를 보지 않으면 며칠 뒤
"데이터가 없다"로 발견됩니다.

SDK를 올릴 수 없다면 업그레이드 후 첫 적재를 **종료코드가 아니라 반영 건수로 판정하세요.**
적재 로그의 "N건 실패" 줄이 0인지 확인하고, dataset의 샘플 수가 실제로 늘었는지 봅니다.
성공으로 끝난 실행에서도 0건일 수 있다는 것이 이 변경의 요지입니다.

**운영 조치** — 위 ④에 걸리는 기존 데이터가 있는지 확인하려면(결과가 0행이면 무시해도 됩니다):

```sql
SELECT DISTINCT bucket, key FROM sample_assets
 WHERE key LIKE '%\%%' ESCAPE '\' OR key LIKE '/%' OR key LIKE '%//%'
    OR key LIKE 'thumb/%' OR key LIKE 'manifests/%' OR key LIKE 'annotations/%'
    OR bucket !~ '^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$';
```

걸리는 행이 있어도 **조회와 seal은 정상 동작합니다.** 그 key로 다시 적재하는 것만 400이 되고, 해당 CAS 객체는 샘플 삭제 시 회수되지 않고 남습니다.

`cas.defaultBucket` 값이 S3 규칙(소문자·숫자·`-`·`.`)을 따르는지도 함께 확인하세요. 어긋나면 기동 로그에 `could not ensure manifest bucket` 경고가 뜨고 seal이 실패합니다(기동 자체는 됩니다).

**운영 조치** — 소유자가 없는(`owner_user_id` NULL) 기존 dataset은 **인증된 누구나 수정·삭제할 수 있습니다.** 소유권 도입 이전에 만들어진 dataset과, 소유자 계정이 삭제된 dataset이 여기 해당합니다. 후자는 계정 삭제 API가 계속 만들어내므로 **이 점검은 업그레이드 시 한 번이 아니라 계정을 삭제할 때마다 다시 해야 합니다.** 현황은 이렇게 봅니다.

```sql
SELECT d.name, coalesce(u.email, '(주인 없음)') AS owner
FROM datasets d
LEFT JOIN users u ON u.user_id = d.owner_user_id
ORDER BY d.owner_user_id NULLS FIRST, d.name;
```

운영 데이터라면 소유자를 지정하세요. 지정하는 API는 없으므로 DB에서 처리합니다.

```sql
UPDATE datasets
SET owner_user_id = (SELECT user_id FROM users WHERE email = 'owner@example.com')
WHERE name = 'my-dataset';
```

- **이메일이 존재하지 않으면 `owner_user_id`가 NULL이 되어 보호가 걸리지 않습니다.** 서브쿼리가 조용히 NULL을 반환하기 때문입니다 — 실행 후 위 조회로 반드시 확인하세요.
- **지정하는 순간 그 dataset은 해당 계정 전용이 됩니다.** 여러 사람이 함께 적재하던 dataset이라면 나머지 인원이 전부 막힙니다. 되돌리려면 `owner_user_id = NULL`로 설정합니다.
- 새로 만드는 dataset은 생성한 계정이 자동으로 소유자가 되므로 이 작업이 필요 없습니다.

**운영 조치** — CVAT 연동을 쓰려면 기존 Secret에 `NEXUS__CVAT__PASSWORD` 키를 추가해야 합니다. 그리고 CVAT 쪽에 ① 서비스 계정, ② CVAT 워커에서 CAS 주소로의 네트워크 도달, ③ smokescreen 사설대역 허용(`SMOKESCREEN_OPTS=--allow-range=...`)이 준비되어야 합니다. ③이 없으면 세션이 `failed`가 되고 이미지 다운로드 실패 사유가 세션 `error`에 기록됩니다.

**주의** — CVAT을 설정하지 않아도 nexus는 정상 동작합니다. 세션 **생성**과 **결과 회수(import)**만 503을 반환하고, 세션 목록·단건 조회·close·delete는 CVAT 없이도 응답합니다(이미 만들어진 세션을 정리할 수 있어야 하기 때문입니다). 카탈로그·업로드·seal·조회는 영향을 받지 않습니다. 설정한 뒤 CVAT이 다운되어도 마찬가지입니다.

**주의** — 이미지·썸네일은 클라이언트가 CAS에서 직접 받으며, 이는 CAS가 익명 GET을 허용하도록 의도된 동작입니다. **위 ①의 인증 강화는 nexus API에만 적용되고 CAS 접근 방식은 바뀌지 않았습니다** — 프론트의 `<img>` 태그는 수정할 필요가 없습니다.
