# nexus-server 차트 변경 이력

각 `##` 섹션이 그대로 해당 버전의 **GitHub Release 본문**이 됩니다
(`scripts/extract-release-notes.sh` 가 발췌 → chart-releaser 가 릴리스 본문으로 사용).

`Chart.yaml` 의 `version` 을 올릴 때 이 파일 맨 위에 섹션을 함께 추가하세요.
섹션이 없으면 릴리스 워크플로가 실패합니다.

해당 사항이 없는 항목도 **"없음"이라고 적습니다** — 도입하는 쪽이 *없었다* 와 *안 썼다* 를
구별할 수 있어야 합니다.

```markdown
## <version>

image: `int2jieun/nexus-server:<tag>` (변경 없음이면 그렇게 적기)

**동작 변경** — 없음
**마이그레이션** — 없음
**설정 키** — 없음
```

### 선택 라벨

세 항목은 **최소**입니다. 더 알려야 할 게 있으면 아래 라벨을 같은 모양(`**라벨** — 내용`)으로
덧붙입니다. 같은 라벨을 여러 번 써서 묶어도 됩니다.

- `**호환성**` — 요구하는 최소 appVersion·이미지 태그, 맞지 않을 때 벌어지는 일
- `**운영 조치**` — 이 버전 때문에 되돌리거나 새로 해야 하는 운영 작업
- `**주의**` — 버전과 무관하게 지켜야 하는 제약을 이 릴리스에서 처음 문서화한 경우

라벨 볼드 안에 수식어까지 넣지 마세요 — `**동작 변경 — 차트**` 가 아니라
`**동작 변경** — 차트` 입니다. 도입하는 쪽이 라벨을 훑어 찾기 때문에 라벨 자체가
고정된 문자열이어야 합니다.

### 마이그레이션 항목 쓰는 법

nexus-server 는 마이그레이션이 바이너리에 임베드되어 **기동 시 자동 적용**되고, 기동이
마이그레이션 성공에 게이트됩니다(`/_internal/health` 가 200이면 적용 완료). 별도 Job 이
없어서 도입하는 쪽에는 릴리스 노트가 유일한 사전 정보입니다. 스키마가 바뀌는 버전이면
아래 세 줄을 함께 적습니다.

- **영향받는 테이블** — 이름을 나열합니다
- **예상 소요시간** — 행 수 기준으로 적습니다. 마이그레이션이 끝날 때까지 Pod 가 Ready 되지
  않으므로 이 시간이 곧 점검창입니다
- **롤백** — 둘 중 해당하는 쪽을 명시합니다
  - **추가만 하는 변경**(테이블·컬럼 추가): 이전 이미지가 새 스키마에서 그대로 기동하므로
    `helm rollback <release> <revision>` 으로 안전하게 되돌아갑니다. "롤백 안전"이라고 적습니다.
  - **파괴적 변경**(삭제·타입 변경·NOT NULL 추가) 또는 **되돌리는 마이그레이션이 없는 경우**:
    **"이 버전은 DB 마이그레이션을 포함하며 이전 버전으로 롤백할 수 없습니다"** 를 그대로
    적습니다. `helm rollback` 은 차트와 이미지만 되돌리고 **이미 적용된 스키마는 되돌리지
    않으므로**, 구버전 이미지가 새 스키마에서 기동하지 못할 수 있습니다. 되돌리려면
    업그레이드 전에 떠 둔 DB 스냅샷(`pg_dump`)을 복원하는 방법밖에 없다는 점을 함께 씁니다.

### 샘플 태그 후보 목록 — `facets` 에 `field=tags`

버전에 실제로 붙어 있는 태그를 모아 줍니다. 0.3.4 의 태그 제외 필터(`exclude_tags`)를 화면에 붙일 때, 사용자가 태그 이름을 외워 타이핑하지 않아도 됩니다.

```
GET /datasets/{id}/versions/{v}/facets?field=tags
GET /datasets/{id}/versions/{v}/facets?field=tags&q=trai    # 타입어헤드
```

응답 모양은 기존 facet 과 같습니다.

```json
{"field": "tags", "values": ["blurry", "night", "train"], "truncated": false}
```

- `q` 는 대소문자를 구분하지 않는 부분일치입니다(다른 facet 과 같습니다).
- 값은 **500개에서 잘리고** 그때 `truncated` 가 `true` 입니다. 그 이상은 `q` 로 좁혀 받으십시오.
- 삭제된 샘플의 태그는 포함되지 않고, 다른 dataset·다른 버전의 태그는 섞이지 않습니다.
- `label` 과 달리 관측 사이드 테이블이 없어 매 호출이 그 버전의 샘플을 훑습니다. 화면의 자동완성처럼 자주 부르는 자리라면 `q` 를 함께 보내십시오.

**호환성** — appVersion 0.1.8 이상. 그 이전 이미지에 `field=tags` 를 보내면 `400` 입니다.

### 적용된 설정 조회 — `GET /api/v1/admin/config-effective` (superuser 전용)

지금 그 프로세스가 **읽은 설정**을 돌려줍니다. 차트 렌더 결과가 아니므로 `extraEnv` 오버라이드도 드러납니다.

**이것을 넣은 이유는 오타가 조용히 삼켜지기 때문입니다.** 서버는 모르는 설정 키를 오류로 만들지 않습니다 — `NEXUS__JWT__TTLHOURS` 처럼 한 글자 틀린 env 는 무시되고 기본값으로 기동합니다. 경고도 없고 기동도 정상이라, 의도한 값이 실제로 걸렸는지 확인할 방법이 없었습니다. `jwt.ttlHours` 는 토큰을 디코드하면 알 수 있지만 `auth.revocationCacheTtlSecs`(권한 회수 상한)는 그마저도 없습니다.

```json
{"database": {"url": "postgres://nexus:<redacted>@db-host:5432/nexus", "max_connections": 16},
 "jwt": {"secret": "<set>", "ttl_hours": 24},
 "auth": {"superuser_email": "<set>", "approval_required": false, "revocation_cache_ttl_secs": 5},
 "cvat": null}
```

- 비밀값은 값이 아니라 `<set>`/`<unset>` 으로만 나오고, `database.url` 은 비밀번호만 가려집니다(호스트·DB 명은 남습니다).
- **`superuser_email` 도 주소가 아니라 `<set>`/`<unset>` 입니다.** 이 서버는 이메일이 곧 권한이라 주소를 아는 것이 표적을 아는 것과 같습니다. 값이 필요하시면 기동 로그에 남습니다.
- `cvat` 이 `null` 이 아니면서 `usable: false` 면 반쯤 채운 설정입니다 — `missing_fields` 가 빠진 항목을 알려줍니다. 그 상태에서 annotation session 라우트는 503 입니다.
- superuser 를 지정하지 않은 배포에서는 누구에게나 403 입니다.

### Python SDK `0.1.8` — `0.1.7` 의 결함을 고쳤습니다

**`int2nexus-sdk 0.1.7` 에서 `ds.samples()` 가 인자와 무관하게 실패합니다** — `TypeError: explore_samples() got an unexpected keyword argument 'exclude_tags'`. 0.3.4 의 태그 제외 필터를 SDK 에 반영하면서 내부 호출부만 고치고 클라이언트 메서드의 인자를 빠뜨렸습니다. 같은 경로를 지나는 `ds.fork()` 와 `ds.backfill_dims()` 도 함께 실패합니다. 적재(`flush`)·업로드·목록 조회는 영향이 없습니다.

**0.3.4 절의 「SDK 는 … `int2nexus-sdk 0.1.7` 부터입니다」를 정정합니다 — `0.1.8` 부터입니다.** 서버는 무관하며, HTTP 로 직접 부르는 경우 `exclude_tags` 는 appVersion 0.1.7 부터 정상입니다.

0.3.4 의 인가 모델 변경이 반영되지 않았던 SDK 문서와 오류 메시지도 함께 고쳤습니다. `flush` 가 `403` 을 받았을 때 "소유자만 가능"이라며 운영자 DB 절차를 안내하던 것이 대표적입니다 — 지금은 역할(`editor` 이상)이 필요하다고 안내합니다.

**운영 조치** — SDK 를 쓰신다면 `0.1.8` 로 올리십시오. 서버만 올려도 동작하지만 `0.1.7` 의 위 결함은 남습니다.


## 0.3.4

image: `int2jieun/nexus-server:0.1.7`
digest: `sha256:e99d79132fb50bd446ed98d1a86b6dc38dfe95618dcabba71e5145279768febc`

태그는 같은 이름으로 다시 밀릴 수 있으므로, 무엇을 돌리고 있는지 고정해야 하면 `image.digest` 에 위 값을 넣으십시오 — tag 대신 그것이 쓰이고 렌더 결과가 `repository@sha256:...` 가 됩니다. cas 차트와 같은 키입니다.

**동작 변경** — 인가 모델이 바뀝니다(아래 첫 항목). `GET /datasets` 등 세 목록에 페이지네이션이 생깁니다(기본 100개). 대량 적재·샘플 목록 조회가 빨라지고, 태그 제외 필터·필터 스코프 일괄 태그·개수 조회·가입 승인 게이트·회원 목록·계정 정지가 생깁니다.
**마이그레이션** — 있음(인덱스 추가·삭제, 컬럼 3개 추가·백필). 아래 참조.
**설정 키** — `auth.approvalRequired`(기본 `false`), `auth.revocationCacheTtlSecs`(기본 5초).

### 인가 모델 — 쓰기는 역할, 삭제는 역할+담당자

`datasets.owner_user_id` 하나가 출처·담당·인가를 겸하던 것을 셋으로 나눕니다.

| 필드 | 뜻 | 인가에 관여 |
|---|---|---|
| `datasets.created_by` | 만든 사람(불변) | 아니오 |
| `datasets.owner_user_id` | 담당자(이관 가능) | 삭제에만 |
| `users.role` | `admin` / `editor` / `viewer` | 예 |

- **쓰기**(적재·수정·seal·태그·fork·서브셋)는 `editor` 이상이면 남의 dataset 에도 됩니다.
- **삭제**(버전·샘플)는 `editor` 이상이면서 담당자 본인이거나 `admin` 이어야 합니다. `viewer` 는 자기가 담당인 dataset 도 지울 수 없습니다.
- **담당자가 비어 있는 dataset 은 `admin` 만 지울 수 있습니다.** 지금까지는 인증된 누구나 지울 수 있었으므로 조이는 변경입니다. `auth.superuserEmail` 도 `admin` 역할도 없는 배포에서는 그런 dataset 을 아무도 지울 수 없게 되니 업그레이드 전에 확인하십시오.
- `POST /api/v1/buckets/ensure` 도 `editor` 이상입니다. CAS 에 버킷을 만드는 쓰기이므로 읽기 전용 계정은 통과하지 못합니다.

기존 계정은 전부 `editor` 로 들어갑니다. `admin` 은 백필하지 않으므로 `auth.superuserEmail` 로 지정한 계정이 그대로 관리 권한을 갖고, 그 계정으로 `POST /api/v1/admin/users/role` 을 불러 다른 사람에게 `admin` 을 줄 수 있습니다.

`auth.superuserEmail` 로 지정한 주소가 그 설정을 켜기 **전에** 이미 평범한 계정으로 가입돼 있었다면, 기동 시 그 계정을 role=admin 으로 맞춥니다(비밀번호는 그대로 둡니다). 이 배선이 없으면 관리 엔드포인트는 되는데 dataset 하나 못 만드는 상태가 될 수 있었습니다.

역할 변경은 최대 5초 안에 반영됩니다(인증이 읽는 사용자 행의 캐시 수명, `auth.revocationCacheTtlSecs`). 설정 superuser 는 재배포 즉시입니다. `0` 으로 두면 매 요청 조회가 되어 즉시 반영되지만, 적재 부하 측정에서 처리량이 20~33% 떨어졌습니다. 조회 자체를 끄는 옵션은 없습니다.

**계정 삭제의 `409` 를 철회했습니다.** `0.3.2` 는 소유 dataset 이 있으면 계정 삭제를 거부했는데, 그 근거(담당자가 비면 누구나 수정·삭제 가능)가 이번 변경으로 사라졌습니다.

**담당 일괄 이관** — `POST /api/v1/admin/datasets/transfer-owner`(관리자 전용, 본문 `from_email`·`to_email`).

**전체 회원 목록** — `GET /api/v1/admin/users`(관리자 전용). `?email=`(부분 검색)·`?role=`로 좁히고 커서로 페이지네이션합니다. 담당자가 회원을 찾아 역할을 바꿀 때 씁니다. `admin/users/pending`(승인 대기만)과는 계층이 다릅니다.

**계정 정지** — `POST /api/v1/admin/users/active`(관리자 전용, 본문 `email`·`active`). 정지하면 다음 요청부터(캐시 수명 안에) 막힙니다 — 이미 발급된 토큰도 포함합니다. 삭제가 아니라 정지라 이메일은 계속 점유되고, 해제하면 그대로 돌아옵니다. `auth.superuserEmail` 로 지정한 계정은 이 경로로 정지할 수 없습니다(403) — 유일한 관리자 부트스트랩 수단이 스스로 잠기는 것을 막기 위해서입니다. 같은 이유로 `POST .../users/role` 도 그 계정을 대상으로 하면 403 입니다.

### 목록 세 개에 페이지네이션이 생깁니다 — 기본 100개

`GET /datasets`, `GET /datasets/{id}/versions`, `GET /datasets/{id}/versions/{version}/subsets` 는 지금까지 전량을 한 응답에 실었습니다. 전량을 받는 것에 의존하는 클라이언트가 있으면 100개에서 잘립니다. `?limit=`(최대 1000)과 `?cursor=<마지막 항목의 id>` 로 이어 받으십시오.

`GET /datasets` 에 필터 둘이 생깁니다. `?mine=true` 는 담당분만, `?unowned=true` 는 담당자가 비어 있는 것만 보여줍니다. 둘 다 기본 뷰용 필터이고 권한이 아닙니다 — 걸지 않으면 지금처럼 전부 보입니다. 함께 주면 `400` 입니다.

### 적재와 샘플 목록 조회가 빨라집니다

`POST /ingest/batch` 가 샘플마다 하던 버전 감사 갱신을 배치당 1회로 모았고, `GET /samples?dataset_id=...` 가 `limit` 과 무관하게 dataset 전체를 훑던 것을 고쳤습니다. API 계약과 반환하는 샘플 집합은 그대로입니다.

**적재** — 샘플 137,000건 규모 테이블, 동시 조회 부하 상태에서 31 → 199.5 samples/sec(6.4배). 문제가 없는 새 DB에서는 273.5 → 508.9(1.86배) — 테이블이 클수록, 동시 쓰기가 같은 버전에 몰릴수록 크게 듣습니다.

**목록 조회** — 대상 dataset 23,001건 기준 쿼리 실행 시간 184ms → 1.5ms(버퍼 92,381개 → 23개, dataset 크기와 무관한 상수).

개선 폭은 데이터 양과 인프라에 따라 다릅니다.

### 가입 승인 게이트 (기본 꺼짐)

`auth.approvalRequired: true` 로 하면 가입은 열어 둔 채 승인 전까지 아무것도 할 수 없게 됩니다. 가입 요청은 계정을 만들되 토큰을 주지 않고 `202` 와 `{"status": "pending"}` 을 돌려주고, 승인 전에는 로그인·토큰갱신이 `403` 입니다. 승인은 `POST /api/v1/admin/users/approve`(본문에 `email`·`role` 필수), 대기 목록은 `GET /api/v1/admin/users/pending` 입니다. 켜려면 `auth.superuserEmail` 도 함께 설정해야 합니다(두 엔드포인트가 관리자 전용).

승인 대기는 다른 `403` 과 본문으로 구분됩니다 — `pending_approval`(비활성 계정은 `forbidden`). 비밀번호가 틀리면 승인 대기 여부와 무관하게 `401` 입니다.

켜기 전에 가입한 계정은 영향받지 않습니다.

**주의** — 켜면 가입 화면이 `202` 를 처리해야 합니다. `nexus-client` 쪽 대응이 준비되기 전에는 켜지 마십시오.

### 태그 제외 필터

`POST .../samples/explorer` body 에 `exclude_tags` 를 주면 그 태그를 하나라도 가진 샘플을 뺍니다. `tags`(포함)와 함께 주면 AND 입니다. 태그가 하나도 없는 샘플은 제외되지 않습니다. 서브셋의 저장 필터도 같은 모양입니다. SDK 는 `ds.samples(exclude_tags=[...])`·`ds.fork(exclude_tags=[...])` 로 `int2nexus-sdk 0.1.7` 부터입니다.

### 새 엔드포인트 셋 — 개수 조회, 필터 스코프 일괄 태그, 내 정보

**`POST /datasets/{id}/versions/{v}/samples/explorer/count`** — `POST .../samples/explorer` 와 같은 body 로 그 필터에 걸리는 샘플 수를 돌려줍니다. 응답은 `{"count": 1204, "exact": true}`. 기본은 10,000 에서 세기를 멈추고 `exact: false` 를 돌려주며, 그때 실제 개수는 `count` 이상입니다. 정확한 값이 필요하면 `?exact=true` — 비용이 결과 크기에 비례하므로 실제로 필요한 곳에만 쓰십시오.

**`POST`/`DELETE /datasets/{id}/versions/{v}/samples/tags`** — 필터에 걸리는 샘플 전체의 태그를 한 번에 고칩니다. body 는 `{"tags": ["reviewed"], "filter": { …explorer 필터… }}`. 기존 `POST /samples/tags`(`sample_ids` 를 받는 것)와는 별개 동작이고 둘 다 남습니다 — 화면에서 고른 것은 그쪽, 필터에 걸린 전부는 이쪽입니다.

대상이 10,000건을 넘으면 `?confirm=<건수>` 가 필수입니다. 없으면 `409` 와 함께 실제 건수를 본문에 실어 돌려주므로 그 값을 붙여 다시 호출하면 됩니다. 값이 실제와 다르면 역시 `409` 이고 아무것도 바뀌지 않습니다. 응답은 `{"updated": 1204}` 만 반환합니다(대상이 크면 샘플 목록 반환은 비용이 큽니다).

`DELETE` 는 원래부터 그 태그를 갖고 있던 샘플에서도 지웁니다 — 이번에 붙은 것과 구분하지 않습니다. 일괄 부여는 새 태그 이름으로 하십시오.

**`GET /api/v1/auth/me`** — 지금 토큰의 주체입니다: `{"user_id", "email", "role", "is_superuser"}`. 역할이 토큰에 없어(회수 지연 때문) 화면이 자기 역할을 알 유일한 통로입니다. 추가 DB 조회는 없습니다.

### 마이그레이션

`015`·`016`·`017` 셋입니다. `015` 는 인덱스 두 개를 만들고 겹쳐서 불필요해진 인덱스 두 개를 지웁니다. `016` 은 `users.is_approved` 를, `017` 은 `users.role` 과 `datasets.created_by` 를 추가하고 `created_by` 를 백필합니다. 기존 컬럼·테이블·제약은 바뀌지 않습니다.

`created_by` 백필은 각 dataset 의 가장 이른 버전의 `created_by` 에서 복원합니다. 저희 인스턴스에서 98% 가 복원됐고, 버전 감사 추적(2026-07-20) 이전 dataset 은 `NULL` 로 남습니다. `owner_user_id` 는 백필 원본으로 쓰지 않았습니다 — 이관된 행은 담당자가 만든 사람이 아닙니다.

- **영향받는 테이블** — `samples`, `dataset_version_samples`, `users`, `datasets`
- **예상 소요시간** — 인덱스 쪽이 두 표 합계 34만 행에 약 4초. 행 수에 대체로 비례하니 100만 행이면 20~30초를 잡으십시오. 컬럼 추가는 기본값이 있는 `ALTER TABLE ADD COLUMN` 이라 테이블을 다시 쓰지 않습니다.
- **롤백** — 기동은 됩니다. 추가된 컬럼은 전부 기본값이 있거나 `NULL` 허용이고, 삭제한 인덱스 둘은 원래 중복이라 이전 이미지가 잃는 것이 없습니다.

  **주의(중요): `auth.approvalRequired: true` 상태에서 되돌리면 승인 대기 중이던 계정이 전부 로그인할 수 있게 됩니다.** 이전 이미지는 `is_active` 만 보고 승인 상태 컬럼을 읽지 않습니다. 다시 올리면 승인 상태가 `FALSE` 로 남아 다시 막히지만, 되돌려져 있던 동안 만들어진 데이터는 남습니다. 되돌리기 전에 `GET /api/v1/admin/users/pending` 으로 대기 계정을 확인하십시오.

  그 밖에 부여한 역할은 무의미해지고 인가가 옛 모델(담당자만 쓰기)로 돌아갑니다.

- **dataset을 삭제해서 빠져나가는 길은 일반적으로 없습니다.** 삭제는 애초에 dataset 단위가 아니라 **버전 단위**이고(남은 버전이 하나도 없을 때 dataset이 함께 사라지는 방식입니다), **sealed 버전은 예외 없이 삭제되지 않습니다** — 그 버전이 dataset의 마지막 버전이어도 `409`입니다. 따라서 sealed 버전을 하나라도 가진 dataset은 소유자 본인도 없앨 수 없습니다.
- **넘기는 쪽에도 전제가 있습니다.** 이관은 **받을 계정이 있어야** 성립합니다(없는 이메일이면 `404`, 자기 자신이면 `400`). 실제 전제는 **"본인 말고 가입된 계정이 최소 하나 더 있을 것"**이고, superuser를 설정해 둔 배포라면 **그 계정이 이 조건을 만족합니다.** `0.3.2`가 "superuser가 없어도 된다"고 적은 것은 *superuser 권한이 필요 없다*는 뜻이지 *다른 계정이 없어도 된다*는 뜻이 아니었습니다.

정리하면 **sealed 데이터를 소유한 채 넘길 상대가 하나도 없는 계정은 삭제할 수 없습니다.**

**이것은 결함이 아니라 의도된 결과입니다.** sealed 버전은 영구 보존이 목적이고, 영구 보존되는 데이터에는 주인이 있어야 합니다. 이 계정을 지우려면 남는 선택지는 둘뿐인데, **(가) 주인을 비운 채 두는 것은 `0.3.2`가 막으려던 바로 그 상태**(주인 없는 dataset = 인증된 누구나 수정·삭제 가능)이고, **(나) sealed 데이터를 지우는 것은 seal 불변식 자체를 깨는 일**입니다. 둘 다 거부보다 나쁘기 때문에 이 조합에서는 계정이 남습니다. `auth.superuserEmail`을 설정해 두면 그 계정이 이관 대상이 되므로 이 상황이 생기지 않습니다.

**주의** — **`README.md`가 `server.port`를 두고 서로 어긋나게 말하던 것을 고칩니다. 바꿀 것은 `server.port` 하나뿐입니다.** values 표는 "바꿀 때 프로브·`service.targetPort`도 함께 바꿀 것"이라고 적었지만, 같은 문서 뒤쪽 절이 적은 쪽이 맞습니다 — 프로브와 Service는 숫자가 아니라 **컨테이너 포트 이름 `http`**를 가리키므로 저절로 따라옵니다. 표를 그대로 따라 프로브나 `targetPort`에 숫자를 박으면 오히려 `server.port`와 어긋나 **파드가 영영 Ready가 되지 않고**, 컨테이너 로그에는 아무 이상이 없어 원인을 찾기 어렵습니다. 같은 README가 경고하던 증상을 표가 유발하고 있었습니다. **이 어긋남은 이번 릴리스가 만든 것이 아니라 그 전부터 있었습니다** — 표를 따라 이미 숫자를 박아 둔 `values-xxx.yaml`이 있다면 그 override를 지우십시오.

**차트에 담긴 문서 링크가 이제 릴리스 태그를 가리킵니다.** `README.md`·`values.yaml`·설치 후 NOTES가 안내하는 아키텍처·사용법 링크가 지금까지 `main` 브랜치를 가리켜, `0.3.3`을 돌리는 사람이 그 뒤에 바뀐 문서를 읽게 됐습니다. 이제 `nexus-server-0.3.3` 태그를 가리키므로 **손에 든 차트와 같은 시점의 문서**가 열립니다. `docs/`는 이미지 때문에(Helm 릴리즈 Secret 1MB 한도) `.helmignore`로 패키지에서 제외되어 링크로만 닿을 수 있는데, 그 링크가 움직이면 제외의 대가만 남습니다. 항상 최신 문서를 보고 싶다면 링크의 태그 부분을 `main`으로 바꿔 여십시오.

**호환성** — appVersion **`0.1.6`** 필요. 구 이미지에서는 소유자 이관 경로가 404이고 계정 삭제는 예전처럼 성공합니다. 차트만 올리고 이미지를 `--set image.tag`로 낮춰 쓰면 이 릴리스가 문서화하는 두 동작이 모두 없는 상태가 됩니다. Python SDK는 `0.1.6`부터 `ds.transfer_owner(email)`(저수준 `client.transfer_dataset_owner(dataset_id, email)`)로 이관을 지원합니다 — 그 이전 SDK에서는 위 `curl` 예시처럼 엔드포인트를 직접 호출하십시오. **SDK는 이 차트와 별도로 발행되므로 인덱스에 올라왔는지 먼저 확인하세요.** `client.delete_account()`는 소유 dataset이 남아 있으면 `NexusError(status_code=409)`를 던집니다.

**주의** — **마이그레이션 예상 소요를 "행 수에 선형"으로 환산하지 마십시오. `0.3.1`의 안내를 여기서 정정합니다.** 그 릴리스는 `0.1.5` 백필 소요를 "샘플 수에 선형, 실측 약 43,800건에서 약 11초"로 적었는데, **계수를 다른 환경에 곱해 쓸 수 있게 적은 것이 잘못이었습니다.** 도입처 실측이 그것을 보여 줍니다.

| 환경 | 행 수 | 소요 |
|---|---|---|
| 우리 개발 DB | 43,810 | 11.2초 |
| 도입처 운영 DB | 69,615 | **4.0초** |

행이 1.6배 많은데 4.5배 빨랐습니다. 우리 값을 행 수로 환산하면 약 18초가 나오지만 실제는 4.0초였습니다. **선형성 자체는 같은 하드웨어 안에서 성립합니다** — 틀린 것은 그 계수가 환경을 넘어 통한다고 읽히게 쓴 쪽입니다. 반대 방향으로 어긋나는 환경도 당연히 있습니다.

그래서 **예산은 넉넉한 쪽으로 잡으십시오.** 여유가 남으면 아무 일도 일어나지 않지만, 모자라면 `startupProbe`가 파드를 kill하고 재기동 → 마이그레이션 재시작이 반복됩니다. 자기 환경의 실제 소요는 첫 기동 로그의 `마이그레이션 완료 applied=<건수> elapsed_ms=<소요>` 중 **`applied`가 0보다 큰 줄**에서 확인할 수 있고, 그 값이 다음 릴리스 예산의 유일한 근거입니다. `values.yaml`의 `startupProbe` 주석도 같은 내용으로 고쳤습니다.

이 릴리스 자체에는 마이그레이션이 없습니다. 따라서 `0.1.5`를 이미 지나온 배포라면 이번 기동에 백필 비용이 들지 않고, 위 정정은 `0.1.5`를 건너뛴 채 이번에 올라오는 배포와 앞으로의 스키마 변경 릴리스에 적용됩니다.

**동작 변경** — **`serviceAccount.automountToken`이 이제 실제로 적용됩니다.** 지금까지 이 값은 `templates/serviceaccount.yaml`에만 렌더됐는데, 그 파일은 `serviceAccount.create: true`일 때만 만들어져 **기본값(`create: false`) 설치에서는 아무 효과가 없었습니다** — 파드는 네임스페이스의 `default` ServiceAccount를 쓰고, 그 ServiceAccount 자체가 `automountServiceAccountToken: false`로 설정되어 있지 않은 한 그 토큰이 그대로 마운트됐습니다(대부분의 클러스터가 이 기본 상태이지만, `default` ServiceAccount를 직접 잠가 둔 클러스터라면 예전에도 토큰이 없었을 수 있습니다). `values.yaml`은 `false`라고 문서화하고 있었으므로, 표준 클러스터라면 이는 그 문서화와 반대되는 동작이었습니다. `0.3.1`부터는 Deployment podSpec에도 `create` 여부와 무관하게 직접 렌더됩니다. Pod에 명시된 값은 항상 ServiceAccount 쪽 설정보다 우선합니다(쿠버네티스 우선순위).

**주의** — **기본 설치의 동작이 뒤집힙니다: "토큰 마운트됨" → "토큰 마운트 안 됨".** `0.3.0` 이하에서는 기본 설치가 (버그로) `default` ServiceAccount의 토큰을 그대로 마운트했습니다. `0.3.1`부터는 문서대로 마운트되지 않습니다. nexus-server 자체는 쿠버네티스 API를 부르지 않아 영향이 없지만, 그 파드의 토큰에 기대던 디버그 컨테이너·사이드카·서비스 메시가 있다면 토큰을 잃습니다 — 필요하면 `--set serviceAccount.automountToken=true`로 되돌리세요. 값이 바뀌는 순간 파드 스펙이 바뀌므로 **롤링 재시작이 한 번 일어납니다.**

**동작 변경** — **`delete_cas` 기본값을 SDK 쪽에 맞춰 "보존"으로 통일합니다.** Python SDK의 고수준 `ds.delete()`는 처음부터 보존이 기본이었습니다 — `delete_cas`를 생략하면 대화형으로 한 번 묻고, 입력이 불가능한 환경에서는 보존을 택했습니다. 어긋나 있던 것은 그 아래 두 층입니다: **서버는 파라미터를 생략하면 지웠고**, SDK 저수준 `client.delete_version()`도 기본값이 삭제였습니다. 이번에 둘을 고수준 SDK와 같은 방향으로 맞춥니다.

| 어떻게 부르는가 | `delete_cas`를 생략하면 |
|---|---|
| `ds.delete(...)` — SDK 고수준 | **달라지는 것이 없습니다.** 예전에도 물었고 지금도 묻습니다 |
| HTTP 직접 호출 — `DELETE /datasets/{id}/versions/{v}`, `DELETE /samples/{sample_id}` | **보존**(이전에는 삭제) |
| `client.delete_version(...)` — SDK 저수준, `0.1.5` | **보존**(이전에는 삭제) |

예전 동작이 필요하면 **`delete_cas=true`를 명시**하십시오(HTTP는 `?delete_cas=true`).

바꾼 이유는 실패 방향의 비대칭입니다 — 잘못된 `false`는 미참조 파일이 남는 것뿐이라 되돌릴 수 있는 스토리지 비용이지만, 잘못된 `true`는 바이트를 되돌릴 수 없이 파괴합니다. 기본값은 되돌릴 수 있는 쪽으로 두는 것이 안전하고, 고수준 SDK가 이미 그렇게 하고 있었습니다.

**영향을 받는 것은 파라미터를 생략한 채 raw HTTP나 저수준 클라이언트를 부르던 호출부입니다.** 그 경로로 삭제하면서 CAS 용량이 함께 정리되는 것에 의존해 왔다면, 업그레이드 후 그 정리가 멈춥니다 — 파일이 안 지워질 뿐 삭제 요청 자체는 그대로 성공하므로 **에러로는 드러나지 않습니다.** 용량 회수가 필요한 호출부를 찾아 `delete_cas=true`를 명시하도록 고치십시오.

**동작 변경** — **readiness 응답에 근거가 실립니다.** `GET /_internal/health`가 성공 시 `{"status":"ok","db":true}`, 실패 시 `{"status":"error","db":false}`(503)를 반환합니다. 지금까지 성공 응답은 `{"status":"ok"}`뿐이라 DB를 실제로 확인하지 않던 구버전 빌드와 구분할 수 없었고, 실패 응답은 `{"error":"database unavailable"}`로 성공과 키 모양이 아예 달랐습니다. **두 본문이 모두 바뀝니다.** 프로브는 상태 코드만 읽으므로 **프로브 동작 자체는 바뀌지 않습니다** — 두 응답의 본문을 직접 파싱하는 스크립트만 고치면 됩니다(특히 실패 본문의 `error` 키를 보던 알림 스크립트는 그 키가 사라집니다).

**동작 변경** — **기동 마이그레이션 로그가 적용 건수를 알려줍니다.** 형식이 `마이그레이션 완료 applied=<건수> elapsed_ms=<소요>`로 바뀝니다. `replicaCount: 1`이면 `applied`가 0보다 큰 기동만 실제 스키마 작업을 측정한 것입니다 — 적용할 것이 없는 기동도 `elapsed_ms`는 찍힙니다(버전 확인 자체의 비용입니다). `applied`를 보지 않고 `elapsed_ms`만 스키마 반영 시간으로 읽으면 착오가 생기는데, 이 필드가 그 착오를 막기 위한 것입니다. **`replicaCount > 1`이면 이 판단이 그대로 맞지 않을 수 있습니다** — `applied`는 이 프로세스의 마이그레이션 실행 동안 DB 전체에 걸린 델타이고, 여러 파드가 동시에 뜨면 sqlx가 advisory lock으로 순서를 정렬하기 때문에, 자신은 아무것도 적용하지 않은 파드도 0이 아닌 `applied`를 보고할 수 있습니다.

**동작 변경** — **annotation 왕복 엔드포인트 추가**(`GET /datasets/{id}/versions/{v}/samples/{sid}/annotations`). 같은 경로의 기존 `PUT`이 `annotation_data` 안에 받는 것과 정확히 같은 모양을 그대로 돌려줍니다 — 평탄화된 샘플 응답을 거치지 않고 annotation을 받아서 고쳐서 그대로 다시 저장할 수 있습니다. Python SDK에도 `ds.get_annotation()`/`ds.save_annotation()`이 함께 준비되어 있습니다(SDK `0.1.5`). **SDK는 이 차트와 별도로 발행되므로 인덱스에 올라왔는지 먼저 확인하세요** — 아직이라면 위 `GET`/`PUT` 엔드포인트를 직접 호출해 같은 일을 할 수 있습니다. **`PUT`은 그 버전의 인스턴스를 병합이 아니라 통째로 교체합니다** — 받은 것 일부만 고쳐 보내면 나머지가 사라집니다.

**동작 변경** — **같은 경로의 `PUT` 응답이 `204 No Content`에서 `200 OK` + 본문으로 바뀝니다.** 본문은 `{"instances": n, "skipped": n, "skipped_reasons": {"missing_label": n, "not_an_object": n, "group_not_an_array": n}}` 형태입니다. 서버는 형식이 어긋난 인스턴스(`label` 필드가 없는 원소, object가 아닌 원소, 값이 배열이 아닌 그룹)를 버리는데, 지금까지는 버리고도 `204`를 돌려줘 클라이언트가 유실을 성공으로 읽었습니다. `PUT`이 통째 교체라 버려진 원소는 "안 들어간" 것이 아니라 **원래 있던 인스턴스가 지워진** 것이므로, 그 수를 응답에 싣습니다. `skipped`가 0이 아니면 그만큼 유실이 일어난 것입니다. **`2xx`로 성공을 판정하는 클라이언트는 영향이 없지만, 상태 코드가 `204`인지로 판정하는 클라이언트는 고쳐야 합니다.** SDK `0.1.5`는 양쪽으로 관대합니다 — 구 서버(`0.1.3` 이하)의 빈 본문에서 예외를 던지지 않고, `skipped`가 0이 아니면 `RuntimeWarning`을 냅니다. **다만 이 관대함은 SDK `0.1.5`부터이므로, 그 버전을 아직 설치할 수 없다면 `204` 판정을 쓰는 자체 클라이언트를 먼저 고쳐야 합니다.**

**마이그레이션** — **테이블 하나가 추가되고 기존 데이터를 한 번 훑습니다**(`dataset_schema_meta_fields`). 기동 시 자동 적용되며 별도 Job은 필요 없습니다.

- **영향받는 테이블** — `dataset_schema_meta_fields`(신규 생성 + 기존 `samples` 백필 스캔)
- **예상 소요시간** — 우리 개발 DB 실측 43,810건에서 11.2초. **이 값을 행 수로 환산해 다른 환경의 예산으로 쓰지 마십시오** — 선형성은 같은 하드웨어 안에서만 성립하고 계수는 환경마다 다릅니다(도입처 운영 DB 실측 69,615건 / 4.0초). 예산은 넉넉한 쪽으로 잡고, `startupProbe` 예산(기본 600초)과 대조할 것. 이 항목은 차트 `0.3.2`에서 정정했습니다(위 `0.3.2` 절)
- **롤백** — **롤백 안전.** 추가만 하는 변경이라 이전 이미지가 새 스키마에서 그대로 기동합니다

**백필 때문에 이 릴리스의 첫 기동만 평소보다 오래 걸립니다.** 마이그레이션이 끝나야 포트가 열리므로 그동안 파드는 Ready가 되지 않고, 그 시간은 그대로 `startupProbe` 예산(기본 `periodSeconds` × `failureThreshold` = 600초)에서 나갑니다. 이 비용은 `applied`가 0보다 큰 기동에서만 듭니다.

`helm rollback`은 안전합니다 — 구 이미지는 이 표를 읽지 않을 뿐이고 표가 남아 있어도 무해합니다(되돌린 뒤 다시 올려도 `ON CONFLICT DO NOTHING`이라 재적용이 안전합니다). 다만 `0.3.0`으로 롤백하면 이미지도 `0.1.3`으로 함께 되돌아가므로, 위에서 바뀐 `delete_cas` 기본값도 함께 되돌아갑니다. 즉 롤백 후에는 `delete_cas`를 생략한 삭제 요청이 다시 **예전처럼 미참조 CAS 객체를 삭제**합니다 — 롤백이 스키마를 해치지는 않지만 이 동작 변경까지 되돌린다는 점은 알고 있어야 합니다.

**동작 변경** — **번들 스키마에 선언되지 않은 `meta` 키도 facet·histogram·필터가 됩니다.** 지금까지 `GET .../facets?field=meta.<키>`는 서버 바이너리에 컴파일된 스키마에 그 키가 선언돼 있어야만 응답했고, 없으면 `400 unknown meta field`였습니다 — 데이터에 키를 하나 더 넣으려면 서버를 다시 빌드해 배포해야 했다는 뜻입니다. 이제 선언되지 않은 키는 그 버전 안의 실제 값 타입을 보고 결정합니다(숫자면 범위, 문자열이면 값 목록, 불리언이면 참/거짓). **선언은 여전히 우선입니다** — 선언된 필드의 동작은 바뀌지 않으며, `capture_time`의 날짜 범위처럼 값만 봐서는 알 수 없는 타입은 계속 선언에서 옵니다. 관측된 문자열은 ISO 8601처럼 보여도 날짜 범위로 승격하지 않고 값 목록으로 다룹니다.

관측 표에도 번들 선언에도 없는 필드는 **계속 `400`입니다**(오타를 빈 facet으로 삼키지 않기 위한 것입니다). 반대로 dataset에는 관측된 적이 있는데 지금 보고 있는 버전에만 값이 없으면 400이 아니라 **빈 결과를 `200`으로** 돌려줍니다.

**다만 키 이름이 `[A-Za-z0-9_]`를 벗어나면(예: `camera-id`, 한글 키, 점이 들어간 키) 이 경로를 타지 못합니다.** 필드명이 SQL에 그대로 들어가는 구조라 화이트리스트로 막혀 있어, 그런 이름으로 facet·histogram을 요청하면 `400 invalid meta field name`입니다. 값 자체는 정상 저장되어 `GET /samples`에는 그대로 보이지만 facet·필터·`GET .../schema` 목록에는 나타나지 않습니다(넣는 쪽과 목록을 만드는 쪽이 같은 규칙으로 거릅니다). 적재 중 그런 키를 만나면 로그에 `meta 키 이름이 [A-Za-z0-9_] 규칙을 벗어나 관측 표에 넣지 않았다` 경고가 **이름별로 한 번** 남으므로, 필드가 안 걸릴 때 여기를 먼저 보세요. 규칙에 맞는 이름으로 다시 적재하는 것 외에 우회 방법은 없습니다.

**동작 변경** — **`GET .../schema`의 `meta_schema.fields`가 데이터에 실제로 있는 필드만 싣습니다.** 지금까지는 선언된 필드 전부를 그대로 실어서, 값이 하나도 없는 필드까지 목록에 남았습니다(그 목록으로 사이드바를 그리면 빈 항목이 자리를 차지합니다). 이제 그 데이터셋에서 관측된 필드만 나오고, 선언되지 않았지만 데이터에 있는 필드는 `"observed": true`가 붙어 함께 나옵니다. 값을 담을 수 없는 타입(객체·배열)은 목록에서 빠집니다 — facet 컨트롤을 그릴 수 없기 때문입니다. 위의 이름 규칙을 벗어난 키도 같은 이유로 빠집니다. **이 목록의 계약은 "여기 실린 것은 facet이 된다"이며, 목록을 만드는 쪽이 facet과 같은 판정 함수·같은 이름 규칙을 씁니다** — 목록에 있는데 누르면 400이 되는 항목은 만들지 않습니다. **선언된 필드의 엔트리는 그대로 실리므로**(타입·enum 값 포함) 기존 소비자가 읽던 형태는 바뀌지 않고, `observed`는 추가 키라 하위호환입니다. 목록이 줄어드는 것 자체가 의도된 변경이니, 사이드바를 이 배열로 그리고 있다면 항목 수가 달라지는 것을 예상하세요.

**설정 키** — 없음. `automountToken`은 이미 있던 키이고 이번에는 배선만 고쳤습니다.

**호환성** — appVersion **`0.1.5`** 필요. 프로브 경로는 `0.3.0`과 동일해 구 이미지에서도 파드가 깨지지는 않지만, 위 `delete_cas` 기본값 변경·readiness 근거·마이그레이션 로그 건수·annotation 왕복 엔드포인트·meta 관측은 구 이미지에는 **존재하지 않습니다.** annotation 왕복 메서드(`ds.get_annotation()`/`ds.save_annotation()`)를 쓰려면 SDK **`0.1.5`** 이상이 필요합니다 — 구 SDK에는 그 메서드 자체가 없습니다. **SDK `0.1.5`는 이 차트와 별도로 발행되므로, 인덱스에 올라왔는지 먼저 확인하세요**(확인: `python -c "import importlib.metadata as m; print(m.version('int2nexus-sdk'))"`).


`--set image.tag=...`로 덮으면 차트가 기대하는 서버 동작과 실제 이미지가 어긋날 수 있습니다. 이 버전은 특히 **차트 쪽 변경(CVAT env 조건부 주입, named port)과 서버 쪽 변경(인증·소유권)이 함께 맞물려** 있습니다. 태그를 지정해야 하는 경우는 롤백처럼 의도적으로 이전 이미지를 쓸 때뿐이고, 그때는 아래 `**호환성**` 항목을 먼저 확인하세요.

**운영 조치** — **업그레이드 전에 무인증으로 nexus를 호출하는 클라이언트가 있는지 점검하세요.** 대시보드, 크론 스크립트, `curl` 기반 헬스체크가 대상입니다. 토큰 없이 조회하던 것이 하나라도 있으면 업그레이드 직후 401로 죽습니다. 프론트는 401(재로그인)과 403(권한 없음)을 구분해 처리해야 합니다 — 둘을 같이 다루면 권한 문제에서 무한 재로그인 루프가 납니다.

**운영 조치** — **적재 경로의 Python SDK를 0.1.2 이상으로 올리세요.** 위 ②가 이 릴리스에서
가장 조용한 실패입니다. 구 SDK는 소유권 거부(403)를 예외로 올리지 않고 종료코드 0으로 끝나서,
적재 CI·크론이 **아무것도 넣지 않은 채 성공으로 표시됩니다.** 로그를 보지 않으면 며칠 뒤
"데이터가 없다"로 발견됩니다.

SDK를 올릴 수 없다면 업그레이드 후 첫 적재를 **종료코드가 아니라 반영 건수로 판정하세요.**
적재 로그의 "N건 실패" 줄이 0인지 확인하고, dataset의 샘플 수가 실제로 늘었는지 봅니다.
성공으로 끝난 실행에서도 0건일 수 있다는 것이 이 변경의 요지입니다.

**운영 조치** — 위 ④에 걸리는 기존 데이터가 있는지 확인하려면(결과가 0행이면 무시해도 됩니다):

```sql
SELECT DISTINCT bucket, key FROM sample_assets
 WHERE key LIKE '%\%%' ESCAPE '\' OR key LIKE '/%' OR key LIKE '%//%'
    OR key LIKE 'thumb/%' OR key LIKE 'manifests/%' OR key LIKE 'annotations/%'
    OR bucket !~ '^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$';
```

걸리는 행이 있어도 **조회와 seal은 정상 동작합니다.** 그 key로 다시 적재하는 것만 400이 되고, 해당 CAS 객체는 샘플 삭제 시 회수되지 않고 남습니다.

`cas.defaultBucket` 값이 S3 규칙(소문자·숫자·`-`·`.`)을 따르는지도 함께 확인하세요. 어긋나면 기동 로그에 `could not ensure manifest bucket` 경고가 뜨고 seal이 실패합니다(기동 자체는 됩니다).

**운영 조치** — 소유자가 없는(`owner_user_id` NULL) 기존 dataset은 **인증된 누구나 수정·삭제할 수 있습니다.** 소유권 도입 이전에 만들어진 dataset과, 소유자 계정이 삭제된 dataset이 여기 해당합니다. 후자는 계정 삭제 API가 계속 만들어내므로 **이 점검은 업그레이드 시 한 번이 아니라 계정을 삭제할 때마다 다시 해야 합니다.** 현황은 이렇게 봅니다.

```sql
SELECT d.name, coalesce(u.email, '(주인 없음)') AS owner
FROM datasets d
LEFT JOIN users u ON u.user_id = d.owner_user_id
ORDER BY d.owner_user_id NULLS FIRST, d.name;
```

운영 데이터라면 소유자를 지정하세요. 지정하는 API는 없으므로 DB에서 처리합니다.

```sql
UPDATE datasets
SET owner_user_id = (SELECT user_id FROM users WHERE email = 'owner@example.com')
WHERE name = 'my-dataset';
```

- **이메일이 존재하지 않으면 `owner_user_id`가 NULL이 되어 보호가 걸리지 않습니다.** 서브쿼리가 조용히 NULL을 반환하기 때문입니다 — 실행 후 위 조회로 반드시 확인하세요.
- **지정하는 순간 그 dataset은 해당 계정 전용이 됩니다.** 여러 사람이 함께 적재하던 dataset이라면 나머지 인원이 전부 막힙니다. 되돌리려면 `owner_user_id = NULL`로 설정합니다.
- 새로 만드는 dataset은 생성한 계정이 자동으로 소유자가 되므로 이 작업이 필요 없습니다.

**운영 조치** — CVAT 연동을 쓰려면 기존 Secret에 `NEXUS__CVAT__PASSWORD` 키를 추가해야 합니다. 그리고 CVAT 쪽에 ① 서비스 계정, ② CVAT 워커에서 CAS 주소로의 네트워크 도달, ③ smokescreen 사설대역 허용(`SMOKESCREEN_OPTS=--allow-range=...`)이 준비되어야 합니다. ③이 없으면 세션이 `failed`가 되고 이미지 다운로드 실패 사유가 세션 `error`에 기록됩니다.

**주의** — CVAT을 설정하지 않아도 nexus는 정상 동작합니다. 세션 **생성**과 **결과 회수(import)**만 503을 반환하고, 세션 목록·단건 조회·close·delete는 CVAT 없이도 응답합니다(이미 만들어진 세션을 정리할 수 있어야 하기 때문입니다). 카탈로그·업로드·seal·조회는 영향을 받지 않습니다. 설정한 뒤 CVAT이 다운되어도 마찬가지입니다.

**주의** — 이미지·썸네일은 클라이언트가 CAS에서 직접 받으며, 이는 CAS가 익명 GET을 허용하도록 의도된 동작입니다. **위 ①의 인증 강화는 nexus API에만 적용되고 CAS 접근 방식은 바뀌지 않았습니다** — 프론트의 `<img>` 태그는 수정할 필요가 없습니다.
