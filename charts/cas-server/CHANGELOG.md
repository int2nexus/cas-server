# cas-server 차트 변경 이력

각 `##` 섹션이 그대로 해당 버전의 **GitHub Release 본문**이 됩니다
(`scripts/extract-release-notes.sh` 가 발췌 → chart-releaser 가 릴리스 본문으로 사용).

`Chart.yaml` 의 `version` 을 올릴 때 이 파일 맨 위에 섹션을 함께 추가하세요.
섹션이 없으면 릴리스 워크플로가 실패합니다.

해당 사항이 없는 항목도 **"없음"이라고 적습니다** — 도입하는 쪽이 *없었다* 와 *안 썼다* 를
구별할 수 있어야 합니다.

```markdown
## <version>

image: `int2jieun/cas-server:<tag>` (변경 없음이면 그렇게 적기)
digest: `sha256:...` (이미지가 바뀐 버전에만. 태그는 다시 밀릴 수 있어 digest 가 유일한 고정점)

**동작 변경** — 없음
**마이그레이션** — 없음
**설정 키** — 없음
```

### 선택 라벨

세 항목은 **최소**입니다. 더 알려야 할 게 있으면 아래 라벨을 같은 모양(`**라벨** — 내용`)으로
덧붙입니다. 같은 라벨을 여러 번 써서 묶어도 됩니다.

- `**호환성**` — 요구하는 최소 appVersion·이미지 태그, 맞지 않을 때 벌어지는 일
- `**운영 조치**` — 이 버전 때문에 되돌리거나 새로 해야 하는 운영 작업
- `**주의**` — 버전과 무관하게 지켜야 하는 제약을 이 릴리스에서 처음 문서화한 경우

라벨 볼드 안에 수식어까지 넣지 마세요 — `**동작 변경 — 차트**` 가 아니라
`**동작 변경** — 차트` 입니다. 도입하는 쪽이 라벨을 훑어 찾기 때문에 라벨 자체가
고정된 문자열이어야 합니다.

### 버전 이력은 여기에만 적습니다

버전 간 비교 및 이전 동작에 대한 설명은 본 문서에만 기재합니다.
`README.md` 와 `values.yaml` 은 **현재 동작만** 서술합니다.

| 문서 | 목적 | 시제 |
|---|---|---|
| `values.yaml` | 설정값 정의 | 현재 — 이 값이 무엇을 하는가 |
| `README.md` | 사용 및 운영 가이드 | 현재 — 어떻게 쓰는가 |
| `CHANGELOG.md` | 변경 이력 기록 | 과거 → 현재 — 무엇이 바뀌었는가 |

단, 현재 설정에 적용된 핵심 제약과 그 당위성은 해당 문서에 남깁니다. 이는 지나간 이력이 아니라 **현재 유효한 판단 근거**이기 때문입니다.

### 마이그레이션 항목 쓰는 법

cas-server 는 기동 시 `CREATE TABLE IF NOT EXISTS` 만 실행하므로 보통 `없음` 입니다.
이미지가 스키마를 바꾸는 버전이면 아래 세 줄을 함께 적습니다 — 도입하는 쪽이 점검창을
잡고 백업 시점을 정하는 데 필요한 정보입니다.

- **영향받는 테이블** — 이름을 나열합니다
- **예상 소요시간** — 행 수 기준으로 적습니다. 스키마 작업이 기동 중에 일어나므로 그
  시간만큼 Pod 가 Ready 되지 않습니다
- **롤백** — **마이그레이션 파일이 하나라도 추가된 버전은 그 이전 이미지로 롤백할 수
  없습니다.** 스키마 호환성과 무관합니다. cas-server 는 `sqlx::migrate!` 를 쓰고, sqlx 는
  기동 시 `_sqlx_migrations` 테이블과 바이너리에 임베드된 마이그레이션 집합을 대조합니다.
  DB 에 바이너리가 모르는 버전이 남아 있으면 다음 오류로 **기동을 거부합니다(exit 1)**:

  ```
  was previously applied but is missing in the resolved migrations
  ```

  즉 인덱스 하나만 추가한 순수 가산형 변경도 롤백이 막힙니다. 그러므로 다음처럼 적습니다.

  - **마이그레이션이 추가된 버전**: **"이 버전은 마이그레이션 N 을 추가하며, 이미지 X 이하로
    롤백할 수 없습니다"** 를 그대로 적고, 롤백 가능한 하한 버전을 함께 씁니다(같은
    마이그레이션 집합을 가진 가장 낮은 이미지). 되돌리려면 `_sqlx_migrations` 에서 해당 행을
    직접 지우거나 업그레이드 전 DB 스냅샷(`pg_dump`)을 복원해야 합니다.
  - **파괴적 변경**(삭제·타입 변경·NOT NULL 추가): 위에 더해 **스냅샷 복원이 유일한 수단**임을
    명시합니다. `helm rollback` 은 차트와 이미지만 되돌리고 이미 적용된 스키마는 되돌리지
    않으므로, 행을 지워 sqlx 가드를 통과해도 구 이미지가 새 스키마에서 오동작할 수 있습니다.
  - **마이그레이션이 없는 버전**: "롤백 안전"이라고 적습니다.

  > **정정 이력 (2026-08-12).** 이 항목은 차트 0.1.23 에서 신설될 때 "추가만 하는 변경은
  > 이전 이미지가 새 스키마에서 그대로 기동하므로 롤백 안전"이라고 적었습니다. **틀렸습니다.**
  > 도입하신 쪽에서 격리 환경으로 반증해 주셨습니다 — 순수 가산형(인덱스 1개 + 함수 1개)인데도
  > `0.1.13` 이 기동을 거부했고, 원인은 스키마가 아니라 위 sqlx 부기 검사였습니다.
  > 그 규칙대로 적힌 라벨을 신뢰해 롤백을 시도하면 복구 압박이 큰 순간에 파드가 뜨지 않습니다.

## 0.1.33

image: `int2jieun/cas-server:0.1.26`
digest: `sha256:28989cbc7484d2ac6c7f355871b3d844dec1b433e14a9eeb63c5cb6d31650710`

**마이그레이션** — 없음. `0.1.26` 은 스키마를 건드리지 않습니다

롤백 하한은 `0.1.25` 그대로입니다(그 하한을 만든 것은 `0.1.32` 의 마이그레이션입니다).
`0.1.26` → `0.1.25` 는 이미지만 되돌리시면 되고 DB 조치가 없습니다.

**설정 키** — 없음

**동작 변경** — GC 회수 후보를 읽는 경로가 생기고 `/_api/gc/orphan-count` 가 폐기됩니다

```
GET /_api/gc/candidates   → {"count": N, "estimated_bytes": M}
```

권한은 `orphan-count` 와 같습니다 — `cas:ReadGc`·`cas:RunGc` 정책 키, root 키, 또는
`secrets.gcToken`(Bearer).

**`/_api/gc/orphan-count` 호출을 그만두십시오.** 그 경로는 `blobs` 전량을 안티조인하므로
비용이 회수 대상 수가 아니라 테이블 크기를 따릅니다. 226 GB 규모에서 30 초
`config.statsStatementTimeoutSecs` 를 넘겨 **항상 `500`** 이고, 그동안 같은 전용 풀을 쓰는
조회가 함께 막힙니다 — `/_api/stats` · `/_api/buckets` · `/_api/buckets/{bucket}/objects` ·
`/_api/backends` 입니다.

응답에 `Deprecation: true` 와 `Link: </_api/gc/candidates>; rel="successor-version"` 이
실립니다. 실패 응답에도 실리므로 500 만 받는 배포에서도 보입니다.

**두 값을 빼서 보지 마십시오.** `candidates` 는 「참조가 0 이 된 시점에 적어 둔 목록」이고
`orphan-count` 는 「지금 참조가 없는 전부」입니다. **어느 쪽도 다른 쪽을 담지 않습니다.**

- 후보에 있는데 고아가 아닌 것 — 지우신 뒤 같은 내용이 다시 올라오면 그 blob 에 참조가
  생깁니다. 큐에서는 GC 가 집을 때 빠지므로 그때까지 남아 있고, 서버가 재확인해서
  건너뜁니다.
- 고아인데 후보에 없는 것 — 큐가 생기기 전부터 고아였던 것과, 마지막 두 참조가 서로 다른
  키에서 동시에 지워져 등록에서 빠진 것입니다. 뒤엣것을 찾는 단계가 `sweep` 입니다.

그래서 차이를 계산하면 그 수가 어느 방향인지조차 해석되지 않습니다.

**동작 변경** — `cas_gc_last_status` 가 실행의 성패만 말합니다

`0`=성공 `1`=**실행** 실패 `2`=실행 중입니다. 항목 몇 건이 실패한 실행은 이제 `0` 입니다.

**`!= 0` 으로 알림을 세우셨으면 부분 실패에 울리지 않습니다.** 울리게 하시려면
`cas_gc_last_errors > 0` 을 함께 거십시오.

**동작 변경** — `cas_gc_last_errors` 지표가 새로 생깁니다

항목 오류 수를 이 지표로 냅니다. `cas_gc_last_status` 에서 갈라 나온 값이라 위 항목과
함께 보십시오. **재기동 뒤 첫 GC 실행까지는 시리즈가 없습니다** — `absent()` 를 걸지
마시고, 그 창에서는 복합 알림의 이쪽 조건이 성립하지 않는다는 것을 감안하십시오.

**동작 변경** — `errors` 의 계수가 **양방향으로** 바뀝니다

여기서 `errors` 는 새 지표만이 아니라 **`GET /_api/gc/last-result` 와
`GET /_api/gc/history` 의 `errors` 필드**입니다. 그 값을 보고 계셨다면 수가 달라집니다.

| | 바뀌는 것 | 방향 |
|---|---|---|
| ⑴ | 같은 blob 이 `orphan`·`sweep` 두 단계에서 실패해도 **1 로 셉니다**(그 전에는 2) | 줄어듭니다 |
| ⑵ | **회수 직전 재확인 실패를 이제 셉니다** | 늘어납니다 |

⑵ 를 따로 적습니다. GC 는 blob 을 지우기 전에 「아직도 참조가 없는가」를 다시 조회하는데,
그 조회가 실패하면 그 전에는 **오류로 세지 않고** 큐로만 되돌렸습니다. 그래서 그 조회만
실패하는 상태가 「오류 0」으로 끝나 큐가 자라는 동안 그 값이 조용했습니다.

**두 방향이 있으니 이력의 수치를 그대로 비교하지 마십시오.** 임계를 새로 잡으실 때는 첫
몇 회 실측을 보고 정하시는 편이 낫습니다.

**동작 변경** — `POST /_internal/gc` 가 `409` 를 내는 경우가 늘었습니다

다른 파드가 GC advisory lock 을 쥐고 있어 **아무것도 시작하지 않은** 호출이 `202` 에서
`409` 로 바뀝니다. 상태 코드를 보는 CronJob 이 있으면 `409` 를 정상 종료로 다루십시오.
`replicaCount: 1` 에서는 이 경우가 생기지 않습니다.

**`202` 응답에 이번 실행의 `id` 가 실립니다** — `{"status":"started","id":1234}`. 새로
생긴 필드입니다. `GET /_api/gc/history` 에 같은 `id` 의 행이 있으므로 **그 값으로 자기
실행 하나만 짚으십시오.** 최신 행을 보면 그 사이에 낀 다른 실행을 자기 것으로 읽습니다.
(차트가 싣는 GC CronJob 은 아직 최신 행으로 판단합니다 — 다음 차트 버전에서 이 `id` 를
쓰도록 바꿉니다.)

**`id` 가 `null` 이면 「돌고 있는지 이 응답으로는 알 수 없다」입니다.**
트리거는 시작 신호를 1 초만 기다립니다. 그때 `/_api/gc/last-result` 의 최신 행으로
판단하지 마십시오 — 다른 실행의 결과를 자기 것으로 읽습니다. 다시 트리거하시는 편이
낫고, 이미 돌고 있으면 `409` 로 끝나므로 안전합니다.

**동작 변경** — 지표 넷이 첫 이벤트 전에도 `0` 으로 나옵니다

`cas_blob_put_bytes_total` · `cas_blob_dedup_total` · `cas_gc_deleted_blobs_total` ·
`cas_gc_freed_bytes_total` 입니다. `anonymousGet: true` 인 배포에서는
`cas_anonymous_get_total` 의 `reason="unsigned"` · `reason="signed_valid"` 두 조합도
함께 나옵니다.

**이 넷에 `absent()` 알림을 거실 수 있게 됩니다.** 어느 지표가 언제 나타나는지는
README 의 「지표가 나타나는 시점」 표에 있습니다 — 아직 `absent()` 를 걸면 안 되는 것이
남아 있습니다.

**수정** — `cas_gc_last_ran_at_seconds` 가 업그레이드 직후 재기동에도 복원됩니다

`0.1.32`(이미지 `0.1.25`)로 올리신 뒤 파드를 재기동하면 이 지표가 하나도 나오지
않았습니다. 그 이미지가 더한 단계 축이 **그 이전 실행 이력에는 없어서** 복원 대상에서
빠졌기 때문입니다. 이제 그 행들을 `multipart,orphan,purge` 로 읽습니다.

**정정** — `0.1.31` 의 GC 소요 계산식에 `sweep` 이 빠져 있습니다

그 절은 실제 소요를 `ms_multipart` + `ms_orphan` + `ms_purge` 로 적었습니다. **`sweep` 이
없던 시절의 식입니다** — 그 단계는 `0.1.32`(이미지 `0.1.25`)가 더했고, `blobs` 전량
안티조인이라 보통 **가장 비싼 단계**입니다. 그 편성으로 `gc.activeDeadlineSeconds` 를
잡으시면 과소 산정되고, `0.1.32` 가 `backoffLimit: 0` 으로 바꾼 뒤라 **시한 초과는 재시도
없는 Job 실패**입니다.

```
실제 소요 = ms_multipart + ms_orphan + ms_purge + ms_sweep
```

`gc.fullSweep` 으로 떼신 배포는 두 Job 의 시한을 각각 그 Job 이 도는 단계의 합으로
잡으십시오.

**정정** — `0.1.30` 의 「돌지 않은 단계는 `null`」은 API 에서 사실이 아닙니다

`GET /_api/gc/last-result` 와 `/history` 는 **돌지 않은 단계도 `0` 으로** 냅니다. 그 절이
「`0` 으로 채우지 않습니다: 「0 ms 에 끝났다」와 구분돼야 합니다」라고 적었는데, `null` 이
되는 것은 **이 컬럼이 생기기 전의 행**뿐입니다.

위 계산식을 API 로 하실 때 이것이 물립니다 — `phases` 에 `sweep` 이 없던 실행의
`ms_sweep` 은 `0` 이고, 그것은 「돌지 않았다」이지 「0 ms 에 끝났다」가 아닙니다. **어느
단계가 돌았는지는 같은 응답의 `phases` 필드로 가르십시오.**

지표는 다릅니다 — `cas_gc_last_duration_ms{phase}` 는 **돌지 않은 단계를 갱신하지
않습니다.** 그래서 그 값은 「그 단계의 마지막 실행」이지 「마지막 실행의 그 단계」가
아닙니다. 분할 편성에서 `{phase="sweep"}` 은 최대 한 달 전 값일 수 있습니다.

**콘솔** — GC 화면이 후보 큐를 읽고, 돌지 않은 단계를 「돌지 않음」으로 표시합니다

GC 화면 맨 위 칸의 이름이 `Orphaned Blobs` 에서 **「회수 후보」**로 바뀌고, 값도
`/_api/gc/candidates` 를 읽습니다 — **표시하는 것이 달라집니다**(위 「두 값을 빼서 보지
마십시오」). 큰 배포에서 그 칸이 비어 있던 것은 `orphan-count` 를 부르고 있었기
때문입니다.

단계별 소요에 `sweep` 칸이 생기고, 그 실행이 돌지 않은 단계는 `0 ms` 대신 「돌지 않음」
으로 나옵니다 — API 는 그 자리에 `0` 을 내므로(위 정정) 화면과 API 가 다르게 보입니다.

실패가 조용했습니다 — 키는 목록에 정상으로 남아 있고 콘솔도 활성으로 표시하는데 그 키를 쓴

같은 이미지의 익명 읽기 계수(아래)도 이 수정에 기댑니다. 만료 판정이 고쳐지지 않은 채

**운영 조치** — 올리기 전에 `gcToken` · `metricsToken` 을 채웠는지 확인하십시오

아래 두 변경이 이 이미지에 함께 들어갑니다. 순서를 거꾸로 하면 GC 가 죽고 메트릭이
열립니다. **`gcToken`·`metricsToken` 채움 → 재시작·검증 → `adminToken` 값 비움 →
이 이미지로 올림** 순서로 하십시오.

**동작 변경** — `adminToken` 이 폐기됐습니다. 어느 경로도 열지 않습니다

`secrets.adminToken` 은 `/_admin/*`(액세스 키 발급·폐기, 정책 관리) · GC
(`POST /_internal/gc` · `GET /_api/gc/*`) · `GET /_internal/metrics` 셋을 **모두 여는**
Bearer 토큰이었습니다. 좁은 토큰을 설정해도 빠지지 않았습니다 — 게이트는 빈 토큰만
후보에서 거르므로 `gcToken` 을 채워도 이 토큰이 GC 를 계속 열었습니다.

`0.1.28` 절에서 폐기를 예고했고, 셋 다 더 좁은 수단이 있으므로 이제 후보에서 뺐습니다.

| 경로 | 이 이미지부터 여는 것 |
|---|---|
| `/_admin/*` | root 액세스 키, `cas:ReadAccessKeys`·`cas:ManageAccessKeys` 를 가진 키 (둘 다 SigV4) |
| GC | 위 둘의 `cas:ReadGc`·`cas:RunGc`, 또는 `secrets.gcToken`(Bearer) |
| `/_internal/metrics` | `auth.metricsToken`(Bearer) 하나뿐입니다. SigV4 분기가 없습니다 |

**`auth-admin-token` Secret 키를 지우셔도 됩니다.** 이 릴리스에서 deployment 의 참조가
`optional: true` 가 됐습니다. `0.1.30` 까지는 필수 참조라 키를 지우면 파드가 기동하지
못했습니다 — 죽은 자격증명을 지우는 것이 장애가 되는 상태였습니다.

정리 순서는 **값 비움 → 다음 sealed-secret 회전에서 키 제거** 입니다. 값만 비운 상태로
두셔도 됩니다.

값이 남아 있어도 렌더·기동은 됩니다. 서버가 무시하고 기동 로그에 그렇게 남기며,
`gcToken`·`metricsToken` 중 비어 있어 끊길 경로를 함께 짚습니다. 키가 아예 없으면 그
경고도 뜨지 않습니다 — 정리가 끝난 상태입니다.

이전 문서에서 이 폐기와 아래 metrics 변경을 「제거 시점 미정」 으로 적었던 자리는 모두
정정했습니다.

**동작 변경** — auth 를 켠 배포에서 `GET /_internal/metrics` 가 닫힙니다

`0.1.23` 까지 이 경로만 「후보가 전부 비면 연다」 였습니다. `/_admin/*` 과 GC 는 auth 를
켜면 토큰이 비어도 `401` 인데 metrics 만 `200` 이었습니다.

| auth | `metricsToken` 이 빈 경우 (이 이미지부터) |
|---|---|
| 켜짐 | `401`. `/_admin/*`·GC 와 같은 판정입니다 |
| 꺼짐(NoAuth) | 무인증으로 열립니다. 기동 로그에 경고가 남습니다 |

NoAuth 배포는 그대로입니다 — 인증을 쓰지 않기로 한 배포의 기존 스크레이프 배선을
업그레이드가 끊지 않게 하려는 것이고, 「빈 토큰 폴백」 의 근거가 실제로 성립하는 쪽은
거기뿐입니다.

**동작 변경** — 차트: GC Job 소요가 실제 GC 소요가 됩니다. `activeDeadlineSeconds` 를 재검토하십시오

`gc-cronjob.yaml` 의 완료 판정이 GC 가 **시작된 것**을 완료로 읽어, Job 이 곧바로
나갔습니다. 그래서 지금까지 **Job 소요는 실제 GC 소요보다 짧게 보였습니다.** 이 버전부터
Job 은 그 실행이 끝날 때까지 기다립니다.

**올리시기 전에 `gc.activeDeadlineSeconds` 가 실제 GC 소요보다 큰지 확인하십시오.**
`0.1.31` 이전 차트를 쓰신 배포는 전부 해당하고, **Job 로그의 소요는 근거가 되지
않습니다.** 실제 값은 `GET /_api/gc/last-result` 의 `ms_multipart` + `ms_orphan` +
`ms_purge` 입니다. Job 이 기다리는 시간은 `activeDeadlineSeconds - 60` 입니다.

`ms_orphan` 이 지배적이면 `gc.phases` 로 그 단계를 `gc.fullSweep` 으로 옮기고 그쪽에
`activeDeadlineSeconds` 를 따로 잡는 편성을 검토하십시오 — `values.yaml` 의 `gc.phases`
주석에 판단 기준이 있습니다.

**시한을 넘기면 Job 이 실패가 아니라 성공으로 끝납니다.** 대기가 끝나 실패로 나간 뒤
재시도가 같은 실행에 부딪혀 `409`(이미 실행 중)를 받고, 그것을 정상 종료로 보기
때문입니다. **회수 자체는 정상입니다** — 서버는 Job 과 무관하게 그 실행을 끝까지 돌리고
결과를 `gc_runs` 에 남깁니다. 잃는 것은 완료 로그와 실패 탐지입니다. Job 로그에는 두
시도가 다 남으므로 구분은 됩니다. 이 판정은 다음 차트 버전에서 가릅니다.

> **덧붙임 (2026-09-01, 발행 뒤 추가 — 이 문단은 `0.1.31` 패키지와 릴리스 본문에 없습니다).**
> 결말이 둘입니다. 재시도 시점에 GC 가 아직 돌고 있으면 `409` 이고, **막 끝나 있으면 `202`
> 를 받아 전량 스캔이 한 번 더 시작됩니다.** 그래서 `activeDeadlineSeconds` 를 예상 소요에
> 가깝게 잡지 마십시오 — 데이터가 늘면 그 띠를 통과합니다. 근본 수정은 `0.1.32` 절입니다.

함께 바뀐 것 — 새 실행이 보이지 않거나 끝나지 않은 채 대기가 끝나면 Job 이 실패로
끝납니다. 예전에는 뒤엣것이 성공이었습니다.

**동작 변경** — 차트: GC CronJob 의 `adminToken` 폴백을 없앴습니다

`gc-cronjob.yaml` 은 `auth-gc-token` 이 비면 `auth-admin-token` 을 실어 보냈습니다. 그
토큰은 폐기됐으므로 이제 보내지 않습니다 — `GC_TOKEN` 이 비면 헤더를 붙이지 않습니다.

**HTTP 결과는 달라지지 않습니다.** 게이트는 받는 토큰이 하나도 설정되지 않았으면 요청이
실어 온 값을 보지 않고 `fail_closed` 로만 판정합니다. 그래서 `gcToken` 이 빈 배포에서는
죽은 토큰을 보내든 헤더를 안 붙이든 결과가 같습니다 — auth 를 켰으면 양쪽 다 `401`,
NoAuth 면 양쪽 다 통과입니다.

바꾼 이유는 **폐기된 자격증명을 매 실행마다 네트워크에 실어 보내지 않기 위해서**이고,
Job 이 인증하는 것처럼 보이지 않게 하기 위해서입니다.

**auth 를 켠 배포에서는 `gcToken` 을 채워야 GC 가 돕니다.** 이것은 이 변경과 무관하게
`adminToken` 폐기에서 오는 결과입니다.

**동작 변경** — 액세스 키 조회의 시각 형식이 RFC3339 로 바뀝니다

`GET /_admin/access-keys` 와 `GET /_admin/access-keys/{key_id}` 의 `created_at` ·
`expires_at` 이 `2026-08-26 01:02:03.000000+00` 에서 **`2026-08-26T01:02:03.000000Z`** 로
바뀝니다. 키 발급 응답과 이 서버의 다른 엔드포인트는 이미 그 형식이었고, 조회만 예외였습니다.

같은 필드가 발급 응답과 조회 응답에서 형식이 달랐기 때문에 파서를 하나만 둔 클라이언트가
한쪽에서 깨졌습니다. 이 절 맨 앞의 만료 판정 결함도 같은 뿌리입니다 — 둘 다 PostgreSQL
의 `timestamptz` 텍스트를 RFC3339 로 그대로 본 것입니다.

**이 두 필드를 파싱하시는 코드가 있으면 확인하십시오.** 문자열로 표시만 하신다면 영향이
없습니다.

**동작 변경** — 콘솔 Keys 화면이 폐기된 키를 기본으로 감춥니다

폐기는 항목을 지우지 않고 `is_active: false` 로 바꿀 뿐이고 만료된 항목도 남으므로 목록은
계속 길어집니다. 정렬이 생성 시각 내림차순이라 **방금 폐기한 키가 맨 위에 앉았습니다.**

이제 기본 화면은 살아 있는 키만 받습니다. 「폐기됨 포함」 을 켜면 전량을 받습니다. 정렬은
활성 → 만료 → 폐기 순이고, 같은 등급 안에서는 생성 시각 내림차순이 그대로입니다.
`key_id` · 설명으로 거르는 입력칸이 붙었습니다.

화면에서 폐기 버튼을 누르면 **그 키가 목록에서 사라집니다.** 기본이 활성만이기 때문이고,
「폐기됨 포함」 으로 다시 볼 수 있습니다.

**동작 변경** — 만료된 키가 「활성」 으로 보이던 것을 고쳤습니다

콘솔은 `is_active` 만 보고 배지를 그렸는데, 그 값은 **폐기 여부만** 말합니다. 만료일이 지난
키도 폐기하지 않았으면 `is_active: true` 라, 요청하면 이미 거절되는 키가 화면에서는 활성으로
보였습니다. 만료된 키로 부르면 `403` 에 에러 코드 `InvalidAccessKeyId` 입니다 — 폐기된 키와
같은 응답이라 응답만으로는 둘이 구분되지 않습니다.

만료된 키는 이제 별도 배지로 표시됩니다. 만료와 폐기는 다른 상태이고 되는 방법도 다릅니다 —
만료는 시각이 지나면 저절로, 폐기는 조작으로.

**동작 변경** — `GET /_admin/access-keys` 에 `?active=` 가 생겼습니다

`?active=true` 는 살아 있는 키만, `?active=false` 는 폐기된 키만 돌려줍니다. **파라미터를
생략하면 지금까지와 같이 전량입니다** — 이 엔드포인트를 부르는 기존 자동화는 그대로
동작합니다.

`active` 는 폐기 여부(`is_active`)만 봅니다. 만료된 키도 폐기하지 않았으면 `active=true` 에
들어옵니다.

정렬은 여전히 생성 시각 내림차순이고 커서는 없습니다.

**동작 변경** — `GET /_admin/access-keys/{key_id}` 가 생겼습니다

키 하나의 상태를 봅니다. 지금까지는 전량 목록을 받아 그 안에서 찾아야 했습니다.

이 엔드포인트는 **폐기된 키도 `200` 이고 `is_active: false` 로 돌려줍니다. `404` 는 그
`key_id` 가 없을 때뿐입니다.** 그 구분이 계약입니다 — 폐기를 `404` 로 답하면 「폐기됐다」 와
「애초에 없다」 가 같아지고, 상위 시스템이 폐기된 키를 없는 키로 보아 그대로 재발급합니다.

응답은 목록의 항목과 같은 모양이고 자격증명은 어떤 형태로도 실리지 않습니다. 권한은 목록
조회와 같습니다 — `cas:ReadAccessKeys` 로 열리고 `cas:ManageAccessKeys` 로도 통과합니다.

**동작 변경** — `/_api/buckets/{bucket}/objects` 의 정렬이 바이너리 순서로 바뀌었습니다

`objects` 정렬과 `after` 커서 비교가 DB 기본 collation 에서 **UTF-8 바이너리 순서**
(`COLLATE "C"`)로 바뀝니다. `ListObjectsV2`(`GET /{bucket}`)와 같은 순서이고, 대소문자·
구두점이 섞인 키에서 결과 순서가 달라집니다(바이너리 순서에서는 `Z` 가 `a` 보다 앞섭니다).

콘솔은 서버가 준 순서를 그대로 그리므로 **파일 목록의 표시 순서가 달라집니다.** 깨지는 것은
없습니다. 이 엔드포인트를 직접 부르는 자동화가 순서에 기대고 있다면 확인하십시오.

같은 조회에 **한 레벨의 상한**이 생겼습니다 — 폴더 10,000 개, 훑는 항목 20,000 개.

**직접 파일이 20,000 개를 넘는 레벨에서는 그 아래 하위 폴더가 하나도 보이지 않을 수
있습니다.** 폴더를 찾으려면 그 레벨의 파일을 하나씩 넘어가야 하는데, 걸음이 파일에서 먼저
소진되기 때문입니다. 예: `img/2026/` 에 사진 25,000 장과 폴더 `img/2026/raw/` 가 있으면 파일
목록은 정상이지만 `raw/` 가 트리에 나타나지 않습니다. 응답에는 그 사실이 실리지 않고
(`prefixes` 는 페이지를 나누지 않는 계약이라 「더 있음」을 적을 자리가 없습니다) **서버 로그의
경고 한 줄이 유일한 신호**입니다. 예전 구현은 느린 대신 그 폴더를 찾아냈습니다.

한 레벨에 파일이 그만큼 쌓이는 구조라면 업그레이드 전에 확인하십시오. 찾는 방법과 상한의
자세한 설명은 README 의 「집계 조회 격리」 절에 있습니다.

**동작 변경** — 하위 폴더가 큰 레벨에서 콘솔 목록이 빨라집니다

같은 조회의 비용이 하위 폴더에 든 파일 수가 아니라 **그 레벨의 항목 수**에 비례합니다.
폴더 안에 파일이 몇십만 개든 그 레벨의 응답 시간에는 영향이 없습니다.

**동작 변경** — 「0 개 달라」 는 요청이 빈 응답으로 끝납니다

목록 세 곳이 같은 모양이었습니다 — `GET /{bucket}` 과 `GET /{bucket}?versions` 의
`max-keys=0`, 그리고 `GET /_api/buckets/{bucket}/objects` 의 `limit=0`. 예전에는 「더 있음」
(`IsTruncated=true` · `has_more=true`)이 나오면서 커서는 실리지 않아, 그 값을 보고 다음 장을
요청하는 클라이언트가 같은 응답을 무한히 받았습니다.

이제 셋 다 항목 없음 · 「더 있음」 거짓 · 커서 없음입니다. 1 이상으로 쓰시는 경우 달라지는
것이 없습니다. 콘솔 목록의 폴더 목록(`prefixes`)은 페이지를 나누지 않으므로 `limit` 과
무관하게 그대로 옵니다.

**동작 변경** — 익명으로 통과한 읽기를 셉니다

`auth.anonymousGet` 을 끄면 서명 없이 읽던 소비자가 그 순간 전부 `403` 이 됩니다. 지금까지
**그게 몇이고 누구인지 알 방법이 없었습니다.**

이제 익명으로 통과한 `GET`/`HEAD` 마다 로그 한 줄(`"anonymous GET"`)과 지표
`cas_anonymous_get_total{reason=...}` 이 나갑니다.

| `reason` | 뜻 | `anonymousGet: false` 로 내리면 |
|---|---|---|
| `unsigned` | 서명이 아예 없었다 | **깨집니다.** 자격증명을 배선해야 합니다 |
| `signed_valid` | 서명이 붙었고 그 키가 유효하다 | 안 깨집니다 (정책이 `GetObject` 를 주는 한) |
| `signed_invalid` | 서명이 붙었는데 키가 폐기·만료됐거나 서명이 틀렸다 | **깨집니다.** 키를 고쳐야 합니다 |

무서명과 「폐기된 키로 서명」을 가르는 것이 요점입니다. 한 값으로 보이면 고치는 방법을 알
수 없습니다 — 앞은 자격증명을 새로 주는 일이고 뒤는 있는 키를 되살리는 일입니다.
`signed_invalid` 는 `warn` 으로, 나머지는 `info` 로 나갑니다.

**판정은 바뀌지 않습니다.** 셋 다 지금처럼 `200` 입니다. `signed_valid` 여도 주체는 익명
그대로라 정책 판정이 되살아나지 않습니다 — 그러지 않으면 `GetObject` 가 없는 키로 읽던
소비자가 이 관측 때문에 `403` 이 됩니다.

```
관리: 액세스 키 발급  key_id=CASK… description=… expires_at=…
관리: 액세스 키 폐기  key_id=CASK…
관리: 정책 추가       key_id=CASK… policy_id=… effect=… action=… bucket=… prefix=…
```

**비밀키는 남기지 않습니다.** 발급 응답이 평문을 내주는 유일한 자리이고, 로그에 한 번 새면

**동작 변경** — 없는 대상에 대한 삭제 요청이 `WARN` 으로 남습니다

```
관리: 없는 액세스 키에 폐기 요청 — 부르는 쪽 목록이 실제와 어긋났을 수 있다
관리: 없는 정책에 삭제 요청
```

**HTTP 응답은 `204` 그대로입니다.** 폐기는 멱등이어야 하고, 이미 없는 것을 없애 달라는
요청은 결과적으로 만족되기 때문입니다. 다만 그 요청이 왔다는 것은 **부르는 쪽이 가진 키
목록이 실제와 어긋났다는 신호**이므로 조용히 넘기지 않습니다.

키 관리를 외부 시스템이 대신하는 배포에서는 이 줄이 곧 "회수됐어야 할 키가 남아 있을 수
있다" 는 뜻이 됩니다.

**주의** — 로그 기반 알림을 쓰신다면 규칙을 확인하십시오

위 `WARN` 두 줄이 새로 생깁니다. `WARN` 수준 전체에 알림을 걸어 두셨다면 이 줄들이 함께
걸립니다. 정상 운영에서는 나오지 않는 줄이지만, 대사(對査) 작업 중에는 반복해서 나올 수
있습니다.

**동작 변경** — 관리 API 를 액세스 키로 열 수 있습니다

`0.1.20` 까지 `/_admin/*`(액세스 키 발급·폐기, 정책 관리)는 `secrets.adminToken` 하나만
받았습니다. 그 토큰은 사람별이 아니라 공용 고정 문자열이라 **관리 조작에 누가 했는지가 남지
않고, 회수하려면 값을 바꿔 재배포해야 하며 그러면 그 토큰을 쓰던 모두가 함께 끊깁니다.**

이제 액세스 키에 관리 정책을 붙여 쓸 수 있습니다.

| 액션 | 대상 |
|---|---|
| `cas:ReadAccessKeys` | 키·정책 목록 조회 |
| `cas:ManageAccessKeys` | 키 발급·폐기, 정책 추가·삭제 **+ 목록 조회** |

`cas:ManageAccessKeys` 하나면 콘솔의 키 화면이 열립니다. `cas:ReadAccessKeys` 는 발급·폐기
없이 목록만 여는 감사·대조 전용 자격증명을 만들 때 씁니다.

사람마다 키를 하나씩 주면 관리자를 둘 이상 둘 수 있고, 한 사람을 끊을 때 나머지가 살아
있습니다. 조작은 그 `key_id` 와 함께 로그에 남습니다.

```
관리: 액세스 키 발급 actor="CASKalice…" key_id=CASKnew…
관리: 액세스 키 발급 actor="<bearer>"    key_id=CASKnew…
```

`adminToken` 은 그대로 받습니다. 그 토큰으로 한 조작은 행위자를 특정할 수 없어 `<bearer>` 로
남습니다. 부트스트랩은 이제 root 키가 맡고, GC CronJob 은 GC 토큰을 쓸 수 있습니다
(아래 두 절).

설정 방법은 차트 README 의 "관리 API 자격증명" 을 참고하십시오.

> **키 관리를 대신하는 외부 시스템에는 `adminToken` 이 아니라 액세스 키를 주십시오.**
> 토큰을 주면 그 시스템이 `POST /_internal/gc`(blob 물리 삭제)까지 여는 자격증명을 상시
> 보유하게 됩니다.

**주의** — 기존 키의 권한은 넓어지지 않습니다

정책의 `"*"` 는 **데이터 평면 액션에만** 걸립니다. 관리 권한은 이름을 명시적으로 적은
정책에만 붙습니다. 그러지 않으면 `action: "*"` 로 발급하신 기존 키 전부가 이 버전에서 키
발급·폐기 권한을 얻게 됩니다.

정책이 붙지 않은 기존 키는 관리 권한을 얻지 않습니다. **root 키는 예외입니다** — 아래
「root 키가 관리 평면 전권을 갖습니다」를 보십시오.

**동작 변경** — 정책의 `action` 이름을 검증합니다

`0.1.20` 까지는 자유 문자열이라 `PutObjekt` 같은 오타가 **영원히 아무것에도 걸리지 않는
정책**을 만들었습니다. 만든 쪽은 권한을 준 줄 압니다.

이제 정의되지 않은 이름은 `400` 입니다. `cas:*` 처럼 관리 액션에 와일드카드를 적는 것도
거절합니다 — 그렇게 적으면 아무것도 매치하지 않아, 관리자를 만들었다고 생각한 배포에
관리자가 없는 상태가 됩니다.

**이미 저장된 정책은 그대로 둡니다.** 지금도 아무것에도 걸리지 않으므로 동작이 바뀌지
않습니다. 다만 그런 정책이 있는지 한 번 확인해 보시는 편이 좋습니다 —
`GET /_admin/access-keys/{key_id}/policies` 로 볼 수 있습니다.

**동작 변경** — root 키가 관리 평면 전권을 갖습니다

`0.1.20` 까지 root 키로 `/_admin/*` 을 부르면 `403` 이었습니다. 이제 `200` 입니다.

권한이 넓어진 것이 아니라 **자격증명 하나를 없앤 것**입니다. 그 전에는 관리자가 되려면
`adminToken` 이 있어야 했고, 그래서 운영자는 root 키와 admin 토큰 둘을 유지해야 했습니다.
root 는 이미 데이터 전체를 지울 수 있으므로 관리 평면을 막아 얻는 것이 없고, root 는 SigV4
신원이라 조작이 `key_id=CASKroot` 로 기록됩니다 — `<bearer>` 보다 낫습니다.

**동작 변경** — auth 를 켜면 root 키가 필수입니다

`secrets.secretMasterKey` 를 설정했는데 `secrets.rootAccessKeyId` 또는
`secrets.rootSecretKey` 가 비어 있으면 **서버가 기동하지 않습니다.**

auth 를 켜면 첫 액세스 키를 만들 부트스트랩 신원이 필요한데, 그 자리를 `adminToken` 이
대신하면 관리 조작이 `<bearer>` 로만 남습니다. root 를 요구하면 불변식이 하나가 됩니다 —
**auth 가 켜져 있으면 귀속 가능한 비상 신원이 언제나 하나 존재합니다.**

`secrets.useExternalSecret: false` 인 경우에는 `helm install`·`upgrade` 가 먼저 막습니다.
기본값(`true`)에서는 실제 값이 sealed-secret 안에 있어 차트가 볼 수 없으므로 검사하지
않습니다 — 그 구성에서는 서버의 기동 검사가 유일한 그물입니다.

NoAuth 배포(`secretMasterKey` 가 빔)는 해당하지 않습니다.

**주의** — sealed-secret 에 root 키가 비어 있지 않은지 이 버전으로 올리기 전에 확인하십시오.
`replicaCount` 가 1 이라 기동 거부는 곧 전면 중단입니다.

**동작 변경** — `adminToken` 이 비면 관리 평면이 `401` 로 닫힙니다

`0.1.20` 까지 **auth 를 켜고 `adminToken` 만 비워 두면 `/_admin/*` 이 자격증명 없이
열렸습니다.** 액세스 키 발급까지 됐습니다. 게이트가 "허용 토큰이 하나도 없으면 내부망
전용 환경으로 보고 통과" 라는 규칙이었기 때문입니다 — 그 가정은 auth 자체가 꺼진 배포를
상정한 것인데, `/_admin/*` 은 auth 를 켰을 때만 붙습니다.

root 키를 설정했으니 그것이 관리자겠거니 하고 토큰을 비워 두는 것이 그 구성에 이르는
자연스러운 경로입니다. 위의 "root 키 필수" 와 함께, 그 경로가 이제 안전합니다.

자격증명 없이 친 결과입니다 (auth 켬, `adminToken` 빔).

| 경로 | `0.1.20` | `0.1.21` |
|---|---|---|
| `GET /_admin/access-keys` | `200` | `401` |
| `POST /_admin/access-keys` | `201` (키가 발급됨) | `401` |
| `POST /_internal/gc` | `200` | `401` |

`GET /_internal/metrics` 는 그대로입니다. 읽기 전용이고, 빈 토큰 폴백은 기존 스크레이프
배선을 위한 것입니다.

**동작 변경** — GC 전용 토큰과 GC 액션이 생겼습니다

GC 경로가 `/_admin/*` 과 같은 자격증명을 쓰고 있었습니다. GC 를 도는 주체는 보통 사람이
아니라 CronJob 인데, 주기 실행을 붙이는 순간 **그 Job 의 시크릿이 액세스 키 발급·폐기
권한까지 들게 됩니다.** GC 에 필요한 것은 blob 물리 삭제 하나뿐입니다.

GC 토큰을 설정하면 GC CronJob 이 그것을 씁니다. 그 토큰으로는 `/_admin/*` 이 열리지
않습니다. 켜지 않으면 `adminToken` 으로 돌아가므로 **기존 배포는 그대로 동작합니다.**

**설정은 한 곳입니다.** Secret 의 `auth-gc-token` 키에 값을 넣으면 서버와 CronJob 이 둘 다
그것을 씁니다. 켜기/끄기 값은 없습니다 — 키가 있는지가 그대로 스위치입니다.
`useExternalSecret: false` 로 차트가 Secret 을 만드는 경우에만 `secrets.gcToken` 에 넣으십시오.

SigV4 쪽으로는 액션 둘이 늘었습니다.

| 액션 | 여는 것 |
|---|---|
| `cas:ReadGc` | `GET /_api/gc/*` |
| `cas:RunGc` | `POST /_internal/gc` **+ GC 조회** |

정책의 `"*"` 는 이 둘도 열지 않습니다 — 관리 평면 액션이기 때문입니다. 콘솔 GC 탭은
`cas:ReadGc` 를 가진 키로 로그인하면 그대로 열립니다(`0.1.20` 까지는 `adminToken` 전용이라
키로 로그인한 사람에게는 잠겨 있었습니다).

**운영 조치** — GC CronJob 에서 키 관리 권한을 떼시려면 sealed-secret 에 `auth-gc-token` 키를
추가하십시오. 그것으로 끝입니다 — 서버와 CronJob 이 같은 키를 읽습니다.
하지 않으셔도 됩니다 — 그러면 `adminToken` 을 계속 씁니다.

**동작 변경** — 콘솔에서 Admin Token 입력창이 사라졌습니다

`0.1.20` 까지 콘솔의 GC 탭과 Keys 탭은 상단 입력창에 `adminToken` 을 넣어야 열렸습니다.
위의 세 절로 관리 평면이 모두 정책으로 열리므로 입력창을 없앴습니다. 화면은 로그인한 키의
정책으로 열립니다.

| 화면 | 필요한 권한 |
|---|---|
| Keys 탭 (목록) | `cas:ReadAccessKeys` 또는 `cas:ManageAccessKeys` |
| 키 발급 · revoke 버튼 | `cas:ManageAccessKeys` |
| GC 탭 · Dashboard 의 Last GC | `cas:ReadGc` 또는 `cas:RunGc` |
| GC 실행 · Dry-run 버튼 | `cas:RunGc` |

root 키는 전부 열립니다. 권한이 없는 화면은 탭이 표시되지 않습니다.

같은 변경으로 버튼 노출이 권한과 맞춰집니다. `0.1.20` 의 콘솔은 `GET /_admin/access-keys` 를
호출해 `200` 이면 화면을 열었는데, 그 경로가 `cas:ReadAccessKeys` 와 `cas:ManageAccessKeys`
양쪽으로 열려 둘이 구분되지 않았습니다. `cas:ReadAccessKeys` 만 가진 키에도 발급·revoke
버튼이 표시됐고, 호출하면 `403` 이었습니다. 이제 그 키에는 버튼이 표시되지 않습니다.

`adminToken` 과 GC 토큰은 서버에서 그대로 동작합니다. 콘솔 입력창만 없앴습니다.

**운영 조치** — 콘솔로 GC·키 관리를 하던 계정에는 해당 권한을 가진 액세스 키가 필요합니다.
`adminToken` 으로는 콘솔에서 열리지 않습니다(`curl` 은 그대로입니다). root 키로 로그인하거나
위 표의 정책을 키에 붙이십시오.

**주의** — `cas:ManageAccessKeys` 는 `cas:ReadAccessKeys` 를 함의하지 않습니다. 정책 모델에
계층이 없습니다. 키 화면과 발급 버튼은 `cas:ManageAccessKeys` 하나로 열리지만
`GET /_api/whoami` 의 `read_access_keys` 는 `false` 입니다. 둘 다 필요하면 둘 다 붙이십시오.

> `0.1.30` 에서 `whoami` 가 라우트 기준으로 바뀝니다 — Manage 만 준 키의
> `read_access_keys` 가 `true` 가 됩니다. 이 절의 서술은 `0.1.28`·`0.1.29` 에 해당합니다.

**동작 변경** — `GET /_api/whoami` 가 생겼습니다

호출한 자격증명의 관리 평면 권한을 반환합니다. 콘솔이 화면 구성에 씁니다. 값은 서버 인가
미들웨어와 같은 판정기로 계산합니다.

```json
{
  "key_id": "CASKroot",
  "is_root": true,
  "can": {
    "read_access_keys": true,
    "manage_access_keys": true,
    "read_gc": true,
    "run_gc": true
  }
}
```

각 값은 그 이름을 명시한 정책에만 `true` 입니다. `action: "*"` 정책은 관리 평면에 걸리지
않아 전부 `false` 이고, NoAuth 배포도 전부 `false` 입니다(신원이 없고 관리 라우터가 붙지
않습니다).

다른 `/_api/*` 와 같이 SigV4 인증이 필요합니다.

**동작 변경** — `secrets.adminToken` 을 폐기 예정으로 표시합니다

이 토큰은 `/_admin/*` · GC · 메트릭 셋을 **모두 엽니다.** 좁은 토큰을 설정해도 빠지지
않습니다 — `secrets.gcToken` 을 채워도 `adminToken` 은 GC 를 계속 엽니다. 게이트는 빈 토큰만
후보에서 거를 뿐이고, 둘 다 값이 있으면 둘 다 받습니다.

폐기하는 이유는 무력해서가 아니라 **셋 다 더 좁은 수단이 있는데 이 토큰만 그 셋을 한꺼번에
열기 때문**입니다. `/_admin/*` 은 root 키와 `cas:ReadAccessKeys`·`cas:ManageAccessKeys` 정책
키가, GC 는 `gcToken` 과 `cas:ReadGc`·`cas:RunGc` 가, 메트릭은 `auth.metricsToken` 이 엽니다.
부트스트랩도 위의 「auth 를 켜면 root 키가 필수」로 root 키가 맡습니다. 그래서 이 토큰은
대체 불가능한 자리를 갖지 않으면서 `gcToken`·`metricsToken` 으로 좁혀 둔 분리만 되돌립니다 —
GC CronJob 에 `gcToken` 만 주더라도 `adminToken` 을 쥔 쪽은 키 발급·폐기까지 할 수 있습니다.

**동작은 이 버전에서 바뀌지 않습니다.** 토큰은 그대로 받고 `gcToken`·`metricsToken` 의
폴백도 그대로입니다. 달라지는 것은 auth 를 켠 배포에서 값이 설정돼 있으면 기동 시 경고가
한 줄 뜨는 것뿐입니다.

```
auth.admin_token이 /_admin/*·GC·메트릭 셋을 모두 엽니다. 좁은 토큰을 설정해도 빠지지
않습니다 — auth.gc_token을 채워도 admin_token은 GC를 계속 엽니다.
...
이미지 0.1.24에서 제거됩니다. 그 전에 auth.gc_token과 auth.metrics_token을 채우고
auth.admin_token을 비우십시오.
```

NoAuth 배포에서는 경고하지 않습니다. 그 모드에는 SigV4 신원이 없어 `adminToken` 이 아직
GC·메트릭을 여는 실제 수단입니다.

**운영 조치** — 제거는 **이미지 `0.1.24`** 입니다. 그 전에 `secrets.gcToken` 과
`auth.metricsToken` 을 채우고 `secrets.adminToken` 을 비우십시오. Secret 키
`auth-admin-token` 자체는 제거 시점까지 필수로 남습니다(`deployment` 가 `optional` 없이
참조합니다) — 값만 비우면 됩니다.

**주의** — 제거되면 `secrets.gcToken` · `auth.metricsToken` 의 `adminToken` 폴백도 함께
사라집니다. 두 값이 비어 있으면 **결과가 서로 다릅니다.**

| 경로 | `gcToken`/`metricsToken` 이 빈 채로 `adminToken` 이 사라지면 |
|---|---|
| `POST /_internal/gc` · `GET /_api/gc/*` | `401` — GC CronJob 이 실패합니다 |
| `GET /_internal/metrics` | **열립니다.** 무인증으로 `200` 입니다 |

메트릭 경로에는 SigV4 분기가 없어 액세스 키로 열리지 않고, 두 토큰이 다 비면 닫히는 것이
아니라 통과시킵니다(기존 스크레이프 배선을 위한 폴백입니다). `/_admin/*` · GC 와 다릅니다.

`auth.metricsToken` 을 반드시 함께 채우십시오. 두 토큰이 다 비면 이미지 `0.1.21` 부터 기동
시 경고가 뜹니다.

```
GET /_internal/metrics가 인증 없이 열려 있습니다 — auth.metrics_token과
auth.admin_token이 둘 다 비어 있습니다.
```

**`0.1.24` 에서는 이 경로도 함께 닫힙니다.** `adminToken` 을 제거하는 같은 릴리스에서
metrics 게이트를 `/_admin/*`·GC 와 같은 판정으로 바꿉니다 — **auth 를 켠 배포**에서 두
토큰이 다 비면 열리는 것이 아니라 `401` 이 됩니다. NoAuth 배포는 지금처럼 열린 채
둡니다(빈 토큰 폴백의 근거가 실제로 성립하는 쪽입니다).

폐기가 곧 노출이 되지 않도록 두 변경을 같은 릴리스에 넣는 것입니다. 다만 그때
`auth.metricsToken` 이 비어 있으면 **스크레이프가 `401` 로 끊깁니다** — 그 전에 채워
두십시오.

**동작 변경** — `auth.adminToken` 게이트를 없앴습니다

GC CronJob 이 Authorization 헤더를 붙일지 정하던 불리언 값입니다. 이제 **Secret 에 값이
있는지가 그대로 스위치**이므로 지웠습니다.

그 게이트는 Secret 과 어긋날 수 있었고, 어긋난 한쪽은 잘못된 상태였습니다.

| Secret `auth-admin-token` | `auth.adminToken` | `0.1.27` | 이 버전 |
|---|---|---|---|
| 값 있음 | `true` | 헤더 붙음 | 같음 |
| 값 있음 | `false` | **헤더 없음 → GC 트리거가 401, 회수가 영영 안 돎** | 헤더 붙음 |
| 빈 값 | 무엇이든 | 헤더 없음 | 같음 |

둘째 줄이 고쳐집니다. `deployment` 는 `auth-admin-token` 을 필수로 참조하므로 그 키에 값이
있으면 **서버는 그 토큰을 요구합니다** — CronJob 만 안 보내는 상태였습니다.

**values 에 `auth.adminToken` 이 남아 있어도 렌더는 실패하지 않습니다**(Helm 이 안 읽는 키를
무시합니다). 정리하실 때 지우시면 됩니다.

트리거가 `401` 이면 Job 이 사유를 적고 실패합니다. 전에는 토큰이 비었는지를 미리 검사했는데,
그 검사는 "비었다" 만 잡고 "틀렸다"·"회전 뒤 어긋났다" 는 놓쳤습니다.

**마이그레이션** — 없음

**설정 키**

| 키 | 기본값 | 뜻 |
|---|---|---|
| `secrets.gcToken` | `""` | GC 토큰 문자열. `useExternalSecret: false` 일 때만 쓰입니다 |
| `image.digest` | `""` | 값이 있으면 `tag` 대신 이것으로 핀합니다 (`repository@sha256:...`) |

태그는 같은 이름으로 다시 밀릴 수 있어 "지금 무엇을 돌리고 있는가" 를 확정하지 못합니다

```yaml
image:

```

참조하므로 **기존 배포는 그대로입니다.**

## 0.1.27

image: `int2jieun/cas-server:0.1.20`

차트 기본값만 쓰신다면 달라지는 것은 이미지 쪽 동작 넷입니다. 새로 추가된 설정 키 넷은
모두 기본값이 이전 동작이라, 손대지 않으면 아무것도 바뀌지 않습니다.

**동작 변경** — `/_api/*` 가 인증을 요구합니다

`0.1.19` 까지는 `auth` 를 켠 배포에서도 이 경로들이 자격증명 없이 응답했습니다. 이제
데이터 평면과 같은 SigV4 서명을 요구합니다.

| 경로 | `0.1.19` | `0.1.20` |
|---|---|---|
| `/_api/stats` · `/_api/buckets` · `/_api/backends` · `/_api/blobs/{hash}` | 무인증 `200` | `403` |
| `/_api/gc/last-result` · `/_api/gc/history` · `/_api/gc/orphan-count` | admin 토큰 | 변화 없음 (admin 토큰) |
| `/_api/auth-mode` | 무인증 `200` | 변화 없음 — 본문은 `{"enabled":true}` 하나입니다 |
| `/_ui` | 무인증 `200` | 변화 없음 — 페이지 껍데기이고 데이터는 서명 요청으로 받습니다 |

뒤의 둘을 연 채로 둔 것은 의도입니다. 콘솔은 자격증명을 물어보기 전에 인증이 켜져 있는지
알아야 하고, 그 판단을 스스로 서명해서 할 수는 없습니다. 무인증 표면이 0 이 되는 것은
아니므로 적어 둡니다.

브라우저 콘솔은 이미 SigV4 를 만들고 있어 그대로 동작합니다.

**동작 변경** — `/_api/buckets` 기본 응답에서 오브젝트 개수가 빠집니다

`object_count` 가 `?counts=true` 를 준 요청에서만 채워집니다. 목록만 필요한 호출이
`object_versions` 를 건드리지 않게 하려는 것입니다. 콘솔은 개수를 함께 청하므로 화면은
그대로이고, 그 요청이 시간 안에 끝나지 못하면 개수만 빠진 목록을 띄웁니다.

**동작 변경** — 중단된 GC 실행이 이력에 남습니다

`0.1.19` 까지는 실행이 **끝날 때만** 기록해서, 프로세스가 중간에 죽으면 행이 아예
없었습니다. 이제 시작 시점에 `status: running` 으로 행을 만들고 끝에서 갱신합니다.
중단된 실행은 `running` 인 채로 `/_api/gc/last-result` 와 `/_api/gc/history` 에 남습니다.

`dry_run` 실행은 이력을 만들지 않습니다. 동시 실행으로 건너뛴 호출도 남기지 않습니다 —
그것은 실패가 아닙니다.

**동작 변경** — GC 완료 로그에 단계별 소요가 찍힙니다

```
GC 단계별 소요  phases=multipart,orphan,purge ms_multipart=2 ms_orphan=13729 ms_purge=213
```

GC 가 오래 걸릴 때 어느 단계인지 이 줄로 갈립니다. `RUST_LOG=info` 가 필요하고 차트
기본값이 그것입니다.

**설정 키** — `gc.phases` · `gc.fullSweep.*`

GC 를 돌릴 단계를 고릅니다. 쉼표 구분 `multipart`, `orphan`, `purge` 이고, 비우면 세 단계
모두 — 기본값이 그것입니다.

`orphan` 만 `blobs` 전체를 훑어 데이터가 늘어나는 만큼 실행 시간이 함께 늘어납니다.
나머지 둘은 인덱스로 처리되어 규모의 영향을 받지 않습니다. blobs 200만 /
object_versions 358만 환경에서 `ms_orphan=13729`, `ms_purge=213~319`, `ms_multipart=2~5`
였고, `multipart,purge` 편성은 324 ms 로 끝났습니다.

```yaml
gc:
  schedule: "0 2 * * 0"
  phases: "multipart,purge"    # 주간: 저렴한 단계만
  fullSweep:
    enabled: true
    schedule: "0 3 1 * *"      # 월간: 전체
```

`fullSweep` 을 켜면 전 단계를 도는 두 번째 CronJob 이 생깁니다. `phases` 에서 `orphan` 을
뺐다면 반드시 켜십시오 — 빼고 끄면 참조가 사라진 blob 이 회수되지 않고 계속 쌓입니다.
그 조합은 막지 않지만 매 실행 경고를 남깁니다.

주기를 정하는 기준은 `docs/usage.md` 의 "주기를 정하는 기준" 을 참고하십시오. 스캔 비용은
회수 대상 개수와 무관하므로, 삭제와 덮어쓰기가 드문 배포라면 자주 훑을 이유가 없습니다.

`phases` 에 정의되지 않은 이름을 적으면 `helm` 이 렌더에서 거부합니다. 공백은 자동으로
제거되므로 `"multipart, purge"` 로 적어도 됩니다.

**설정 키** — `config.multipartTtlSecs`

GC 가 미완료 멀티파트 업로드를 만료로 보는 기준(초). 기본 `86400`(24시간)으로 이전과
같습니다. `0.1.19` 까지는 코드 고정값이라 바꿀 수 없었습니다.

시험 환경에서 짧게 잡으라고 뺀 값입니다. **운영에서 짧게 잡지 마십시오** — 진행 중인
업로드의 파트가 조립 전에 회수되면 그 업로드가 `5xx` 로 실패합니다.

**설정 키** — `config.consoleEnabled`

`/_ui` 와 콘솔용 `/_api/*` 를 마운트할지. 기본 `true` 로 이전과 같습니다.

`false` 로 두면 그 경로들에 핸들러가 붙지 않습니다. 인증이 꺼진 배포에서는 `404`, 켜진
배포에서는 인증 미들웨어가 먼저 걸러 `403` 이고, 어느 쪽이든 유효한 자격증명으로도
응답하지 않습니다.

`/_api/gc/*` 와 `/_internal/*` 는 admin 토큰 라우터에 있어 남으므로, **콘솔을 끄고도
GC CronJob 을 그대로 쓸 수 있습니다.**

**마이그레이션** — 없음

**호환성** — 위 설정 키 넷은 이미지 `0.1.20` 이상이 필요합니다

그 이하 이미지는 `multipart_ttl_secs` 와 `console_enabled` 를 무시하고, `phases` 를 받은
`/_internal/gc` 는 그 파라미터를 무시한 채 전 단계를 돕니다. 차트는 `image.tag` 로 버전을
핀하므로 함께 올리면 문제되지 않습니다.

**운영 조치** — `/_api/*` 를 콘솔 밖에서 호출하는 곳이 있는지 확인하십시오

스크립트나 모니터링이 `/_api/stats` · `/_api/buckets` 등을 자격증명 없이 치고 있었다면
이 버전에서 `403` 이 됩니다. SigV4 서명을 붙이거나, 해당 경로가 admin 토큰 쪽
(`/_api/gc/*`)이면 지금처럼 토큰만으로 됩니다.

## 0.1.26

image: `int2jieun/cas-server:0.1.19`

이미지 릴리스입니다. 차트 템플릿은 바뀌지 않았고, `image.tag` 와 `appVersion` 만 올렸습니다.

**동작 변경** — 인증 실패가 원인별로 다른 에러 코드를 반환합니다

`0.1.18` 까지는 원인과 무관하게 전부 `403 InvalidAccessKeyId` + `invalid credentials` 였습니다.
원인이 다른 실패를 클라이언트도 운영자도 구분할 수 없었습니다.

| 무엇 | `0.1.18` | `0.1.19` |
|---|---|---|
| Authorization 헤더·presigned 쿼리 형식 오류 | `403 InvalidAccessKeyId` | `400 AuthorizationHeaderMalformed` |
| 서명 불일치 | `403 InvalidAccessKeyId` | `403 SignatureDoesNotMatch` |
| 자격증명 없음 | `403 InvalidAccessKeyId` | `403 AccessDenied` |
| 요청 시각이 15분 넘게 어긋남 (헤더 인증 경로) | `403 InvalidAccessKeyId` | `403 RequestTimeTooSkewed` |

상태코드가 바뀌는 것은 첫 줄 하나뿐입니다. 나머지는 403 그대로이고 코드 문자열만 갈립니다 —
AWS S3 도 서명 불일치에 403 을 쓰므로 규약을 따른 것입니다. 키가 없는 것·비활성인 것·
유효기간이 지난 것은 클라이언트에게 계속 하나로(`InvalidAccessKeyId`) 보입니다.

**동작 변경** — SigV4 의 region 을 더 이상 검사하지 않습니다

`0.1.18` 까지는 자격증명 스코프의 region 이 `cas-default` 가 아니면 거부했습니다. 서명 키는
클라이언트가 선언한 region 으로 유도하므로 이 검사는 암호학적으로 필요한 것이 아니었고,
S3 호환 클라이언트의 기본 설정(boto3 는 지정하지 않으면 `us-east-1`)을 막고 있었습니다.

이제 임의 region 으로 서명해도 동작합니다. `service` 는 계속 `s3` 여야 합니다.

**동작 변경** — 조인이 필요한 용량 세 값만 옵트인이 됩니다

**`blobs` 테이블 단독 집계는 그대로 나옵니다.** `blob_count` 와 `physical_size_bytes` 는
조인이 없어 뺄 이유가 없었고, 콘솔의 `Blobs (physical)` 카드도 그대로입니다.

`null` 이 되는 것은 `object_versions` × `blobs` 조인을 요구하는 셋뿐입니다.

| 엔드포인트 | 필드 | 뜻 |
|---|---|---|
| `/_api/stats` | `logical_size_bytes` | live 오브젝트가 참조하는 논리 용량 |
| `/_api/stats` | `live_physical_size_bytes` | 그중 고유 blob 의 용량 |
| `/_api/buckets` | `total_size_bytes` | 버킷별 용량 |

`?sizes=true` 를 붙이면 채워집니다. 한 문장에 두면 규모가 커졌을 때 이 셋이
`statement_timeout` 에 걸리면서 조인이 필요 없는 나머지 값까지 함께 죽어 화면 전체가
비었습니다 — 그것이 이 변경의 이유입니다.

**콘솔에서 달라지는 곳은 둘입니다.**

- `Dedup Ratio` 카드가 **개수 기준**으로 먼저 그려집니다. 용량 기준은 "용량 기준 계산"
  링크를 눌렀을 때 따로 요청합니다.
- **버킷 목록에서 버킷별 용량이 사라집니다.** 목록은 `?sizes=true` 를 붙이지 않으므로
  오브젝트 개수만 표시됩니다. 그 값을 되살리려면 조인이 필요하고, 지금 규모에서는
  인덱스가 들어가야 30초 안에 끝납니다 — 다음 이미지에서 인덱스와 함께 다룹니다.

`?sizes=` 는 `true`/`false` 만 받습니다. `?sizes=1` 이나 값 없는 `?sizes` 는 `400` 이고
그 응답 본문은 XML 이 아닌 평문입니다.

**동작 변경** — 그 밖의 응답·로그

- 등록되지 않은 `/_api/*` 경로가 `404` 를 반환합니다. `0.1.18` 까지는 무인증 요청에
  내부 타입명이 담긴 `500` 이 나갔습니다.
- `/_api/backends` 의 `endpoint_url`(백엔드 스토리지 실주소)이 admin 토큰이 있을 때만
  나갑니다. 토큰 없이 부르면 그 필드가 `null` 입니다. 목록·용량은 그대로입니다.
- 인증 실패 로그에 `reason` 과 `key_id` 가 붙습니다. `reason` 은 고정 문자열이라 알림
  규칙을 걸 수 있습니다: `no_credentials` · `malformed_header` · `unknown_key` ·
  `key_inactive` · `key_expired` · `secret_undecryptable` · `clock_skew` ·
  `presigned_expired` · `signature_mismatch`. 인증 처리 자체가 실패하면(예: 인증 조회 중
  DB 오류) `other` 이고, 그때는 응답도 `500` 입니다. `key_id` 는 요청이 **주장한** 값이고
  검증된 것이 아닙니다.
- `db_acquire_timeout_secs` 관련 기동 경고가 없어졌습니다. 절대 임계값(`>= 12`)이라
  권장값대로 맞춘 배포에서도 떴고, 서버 기본값이 30 이라 사실상 항상 떴습니다.
  아래 `readiness_probe_timeout_secs` 를 설정하면 실제 프로브 값과 비교합니다.
- GC 결과의 `errors` 가 세는 대상이 늘었습니다. 파트 목록을 DB 에서 읽지 못한 경우가
  새로 잡힙니다. `0.1.18` 은 애초에 그 목록을 읽지 않았으므로(정리를 프리픽스 열거로만
  했습니다) 셀 것도 없었습니다. **값이 올라간 것이 곧 악화는 아니고, 예전에는 존재하지
  않던 판정 지점이 생긴 것입니다.**
- 파트 정리가 실패한 업로드는 `ListMultipartUploads` 에 남습니다. 완료된 업로드가 그
  목록에 보일 수 있고, 정리가 성공하면 곧바로 사라집니다. 그 목록으로 lifecycle 집행을
  판정하실 때는 `errors` 가 0 인지 함께 보십시오.

**동작 변경** — 완료된 업로드의 `upload_id` 가 잠시 살아 있습니다

`0.1.19` 는 멀티파트 완료 시 **커밋을 먼저 하고 파트를 나중에 지웁니다.** 커밋이 실패했을 때
파트가 남아 있어야 클라이언트가 재시도할 수 있기 때문입니다 — `0.1.18` 은 순서가 반대라,
커밋이 실패하면 조립본과 파트가 함께 사라져 그 업로드를 되살릴 수 없었습니다.

대가로, 파트 정리가 끝나기 전까지 그 `upload_id` 가 유효한 상태로 남습니다. 그 사이에는
`UploadPart` 가 받아들여지고 `CompleteMultipartUpload` 를 다시 부를 수 있습니다.
**실제 S3 는 완료 후 `NoSuchUpload` 를 반환하므로 이 부분이 다릅니다.**

- **정상 경로에서는 밀리초 단위**입니다. 정리가 끝나면 곧바로 사라집니다.
- **정리가 실패하면 GC 가 치울 때까지**입니다. 서버는 24시간이 지난 업로드를 GC 로
  정리하므로, 주간 CronJob(`gc.schedule`) 기준 최대 8일가량입니다.
- 같은 파트 목록으로 재시도하면 **같은 내용이라 결과가 같습니다.** 내용이 달라지려면
  완료한 뒤에 파트를 더 올리고 다시 완료해야 합니다.

닫으려면 "완료됨" 표시를 DB 에 두어야 하고 그것은 마이그레이션입니다. 그러면 이 버전의
롤백 안전이 깨지므로, 이번에는 넣지 않고 여기에 적습니다.

**호환성** — 응답 필드 셋이 nullable 이 됩니다

`logical_size_bytes` · `live_physical_size_bytes` · `total_size_bytes` 를 숫자로 기대해
파싱하는 소비자는 `?sizes=true` 로 옮겨야 합니다. 콘솔 화면은 이 릴리스에서 함께
고쳤으므로 조치가 필요 없습니다.

상태코드로 분기하는 클라이언트 래퍼가 있으면 위 첫 표의 `403` → `400` 한 줄을 확인하십시오.
형식 오류는 재시도해도 성공하지 않으므로 400 이 맞습니다.

**마이그레이션** — 없음. 롤백 안전

이 버전은 마이그레이션 파일을 추가하지 않습니다. 이미지 `0.1.18` 로 되돌릴 수 있습니다.

다만 **DB 에 남는 상태가 하나 있습니다.** 파트 정리가 실패하면 완료된 업로드의
`multipart_uploads` 행이 남습니다. `0.1.18` 로 롤백하면 그쪽 GC 는 목록 API 에 의존하는
옛 정리 경로로 그 행을 집으므로, `list-objects-v2` 가 실패하는 백엔드에서는 매 GC 패스마다
`errors` 가 올라갑니다. 롤백 후 `errors` 가 계속 오르면 이것일 수 있습니다.

**설정 키** — `readiness_probe_timeout_secs` 하나가 늘었습니다

이미지 쪽 키이고 차트 값으로는 노출하지 않습니다. 이 배포의 `readinessProbe.timeoutSeconds`
값을 넣으면 서버가 기동 시 `db_acquire_timeout_secs` 와의 관계를 실제로 검사하고, 어긋날
때만 경고합니다. 넣지 않으면 검사하지 않습니다 — 프로브 값은 서버가 볼 수 없으므로
추측으로 경고하지 않습니다.

```yaml
extraEnv:
  - name: CAS__READINESS_PROBE_TIMEOUT_SECS
    value: "22"
```

차트는 렌더 시점에 이미 같은 관계를 검증합니다(`readinessProbe.timeoutSeconds` >
`config.dbAcquireTimeoutSecs`). 이 키는 그 검증이 보지 못하는 `extraEnv` 오버라이드를
잡기 위한 것이므로, 차트 값만 쓰신다면 설정하지 않아도 됩니다.

**주의** — 유효한 액세스 키 ID 를 열거할 수 있게 됩니다

"키 없음"(`InvalidAccessKeyId`)과 "서명 불일치"(`SignatureDoesNotMatch`)가 갈리므로,
임의의 키 ID 로 아무 서명이나 보내면 그 키의 존재 여부를 알 수 있습니다. AWS S3 도 같은
대가를 치르고 구분하며, 진단 가치가 크다고 판단해 그렇게 했습니다. 받아들이기 어려우면
알려 주십시오 — 로그 분리만 남기고 응답을 되돌리는 형태도 가능합니다.

이 서버에는 인증 시도에 대한 속도 제한이 없습니다. `service.type` 을 `ClusterIP` 로 두고
네트워크 경계 뒤에 놓는 기존 권고가 그대로 유효합니다.

**호환성** — 차트 자체는 0.1.17 이미지로도 렌더·기동됩니다. 다만 아래 항목 중

`auth-metrics-token` 을 넣으면 서버가 무시하므로 그 토큰으로 스크레이프하면 401 이
되고, 새로 추가된 `config.stats*` 키도 무시됩니다.

**운영 조치** — 이 릴리스에는 **되돌릴 수 없는 데이터 유실 경로 수정**이 포함됩니다
(아래 첫 항목). 이미지를 함께 0.1.18 로 올리십시오. 차트만 올리면 그 수정은 들어가지 않습니다.

**동작 변경** — 이미지 0.1.18: 커밋 응답이 유실될 때 살아있는 blob 을 지우던 문제를 고쳤습니다

메타데이터 커밋이 실패로 보고되면 방금 쓴 blob 을 되돌립니다. 그런데 **커밋 실패가
"커밋되지 않음"을 뜻하지는 않습니다** — PostgreSQL 이 커밋을 완료한 뒤 커넥션이 끊겨
응답만 유실되는 경우가 있습니다. 그때도 blob 을 지우고 있었습니다.

결과는 **커밋된 객체가 삭제된 파일을 가리키는 상태**입니다. GC 의 orphan 판정은 살아있는
참조를 보므로 이 blob 을 영원히 손대지 않고, 삭제가 성공하면 로그도 남지 않았습니다.
발견되는 시점은 최종 사용자가 그 객체를 GET 할 때입니다.

이제 되돌리기 전에 blob 레코드의 존재를 확인해 세 갈래로 갈립니다.

| 확인 결과 | 판단 | 조치 |
|---|---|---|
| 레코드 없음 | 트랜잭션이 진짜 롤백됐다 | 지운다 (기존 동작) |
| 레코드 있음 | 커밋 응답 유실 또는 동시 커밋 | **보존** + 경고 로그 |
| 확인 실패 | 판별 불가 | **보존** + 경고 로그 |

불확실할 때 보존하는 쪽을 택했습니다 — 회수되지 않은 blob 은 비용이고 실체 없는
참조는 되돌릴 수 없는 유실이라 비대칭이 명확합니다. 멀티파트 완료 경로에도 같은 수정이
들어갔습니다.

관련해 로그 문구 하나를 정정했습니다. 커밋 실패 후 정리까지 실패한 경우를
"GC 대상으로 남김"이라고 적었는데 **사실이 아닙니다** — GC 는 blob 레코드를 기준으로
열거하므로 레코드가 없는 파일은 볼 수 없습니다. "GC 가 볼 수 없는 미추적 blob으로 남음"
으로 고쳤습니다.

**동작 변경** — 이미지 0.1.18: 집계 조회를 커넥션 1개짜리 별도 풀로 격리했습니다

`/_api/stats`, `/_api/buckets`, `/_api/buckets/{bucket}/objects` 의 서브폴더 조회,
`/_api/backends` 의 blob 집계, orphan 카운트는 전 테이블 집계입니다.
2026-08 운영 사례에서 이 경로의 조인이 디스크로 스필하며 임시 파일 **352.8 GB** 를 만들고
적재를 **2시간 55분** 막았습니다. **파드 재시작으로 끊을 수 없었습니다.**

기전은 타임아웃 부재만이 아닙니다. 요청 타임아웃은 클라이언트에게 응답을 돌려주고
핸들러를 취소할 뿐 쿼리는 DB 에서 계속 돕니다. 그리고 **취소된 쿼리의 커넥션은 닫히지
않고 유휴 풀로 반납됩니다** — 다음에 그 커넥션을 뽑은 무관한 요청이 버려진 문장이 끝날
때까지 막힙니다. 즉 타임아웃된 집계 하나가 풀 커넥션 하나를 오염시킵니다.
`/_internal/health` 가 같은 풀을 쓰기 때문에, **인증 없는 GET 한 건이 파드를 Service
엔드포인트에서 밀어낼 수 있었습니다**(`replicaCount: 1` 이라 그것이 전면 중단입니다).

그래서 타임아웃만으로는 닫히지 않고 격리가 필요합니다.

| 장치 | 값 | 역할 |
|---|---|---|
| 커넥션 1개 | 고정 | 동시성 상한. 대시보드를 몇 번 새로고침해도 DB 에 도는 집계는 항상 1건 |
| `statsStatementTimeoutSecs` | `30` | PostgreSQL 이 실제로 문장을 취소하게 하는 유일한 수단 |
| `max_parallel_workers_per_gather = 0` | 고정 | `work_mem` 은 워커마다 따로 쓴다 — 워커가 붙으면 스필이 배가된다 |
| `statsWorkMemMb` | `0` | 올리면 해시 조인 배치 수가 줄어 스필이 준다 |
| 캐시 60초 + single-flight | `/_api/stats` 만 | 동시 요청이 쿼리를 하나만 띄운다. 나머지 넷은 캐시되지 않는다 |

캐시는 이전부터 60초로 있었으나 **동시 요청 중복 제거가 없었습니다** — 동시에 N 건이
들어오면 N 건 모두 캐시 미스로 판정하고 N 건 모두 같은 쿼리를 띄웠습니다. 또 캐시 쓰기가
성공 경로에만 있어 **요청 타임아웃보다 느린 쿼리는 구조적으로 절대 캐시되지 않았습니다.**
실패 시 지난 값을 stale 로 제공하고 짧은 쿨다운을 두어 재질의 폭주를 막습니다.

파드당 PostgreSQL 커넥션이 1 늘어납니다: `dbMaxConnections + gcDbMaxConnections + 1`.
기본값 기준 `20 + 2 + 1 = 23` 입니다.

**동작 변경** — 이미지 0.1.18: DB 커넥션 풀 고갈이 500 대신 `503 SlowDown` 이 됩니다

풀에서 커넥션을 얻지 못한 요청은 지금까지 `500 InternalError` 로 나갔습니다.
이것은 서버 결함이 아니라 **일시적 자원 부족**입니다. 커넥션은 요청당이 아니라 쿼리당
잡히므로, 이 오류는 "DB 가 순간적으로 처리량을 못 낸다"는 뜻입니다.

- 상태 코드가 `503`, S3 오류 코드가 `SlowDown` 이 됩니다. **재시도 여부는 바뀌지 않습니다** —
  `500 InternalError` 도 `503 SlowDown` 도 모든 AWS SDK 가 기본으로 재시도합니다.
  바뀌는 것은 **분류**입니다. `SlowDown` 은 각 SDK 의 throttling 코드 목록에 들어 있고,
  판정 기준은 상태 코드가 아니라 이 코드 문자열입니다.

  기본 설정에서 실제로 달라지는 것:

  | 클라이언트 | 변화 |
  |---|---|
  | adaptive 모드를 켠 클라이언트 | 클라이언트측 rate limiter 작동 (throttling 분류에만 반응) |
  | Java v2 (기본) | 재시도 quota 토큰 0개 소모 (일반 5xx 는 5개), 백오프 하한 500ms |
  | Rust SDK | 토큰 5개 소모 (5xx 는 10개) — 재시도 예산 소모 절반 |
  | **boto3 기본 · Go v2 기본** | **이전과 동일** — 백오프 공식이 오류 종류를 보지 않습니다 |

  더 큰 차등화는 AWS 의 2026 재시도 동작이 기본값이 될 때 오고, 지금은
  `AWS_NEW_RETRIES_2026=true` 옵트인입니다. 즉 **이 변경의 즉효는 운영자 쪽**입니다 —
  아래 로그 레벨 항목이 그것입니다.
- 로그 레벨이 `error` 에서 `warn` 으로 내려갑니다. 설계된 배압을 오류로 남기면
  진짜 장애 신호가 파묻힙니다.
- 풀 고갈이 아닌 DB 오류는 그대로 `500 InternalError` 입니다 — 재분류를 넓게 하면
  진짜 DB 장애가 "잠시 후 재시도"로 위장됩니다.

2026-08 운영 실측에서 8.4시간에 4,674건이 전부 500 으로 나갔습니다. 적재 클라이언트가
그 500 을 재시도했는지 건너뛰었는지 판단할 근거가 없는 상태였습니다.

**동작 변경** — 이미지 0.1.18: readiness 가 "풀 포화"와 "DB 단절"을 구분합니다

`/_internal/health` 가 두 경우를 갈라 응답합니다.

| 상황 | 응답 | 근거 |
|---|---|---|
| 커넥션 풀 포화 (DB 는 살아있음) | `200`, `status: "saturated"` | 프로세스는 정상 서빙 중이다 |
| DB 에 못 닿음 | `503`, `status: "degraded"` | 의존성이 죽었다 |

**두 경우는 오류 종류로 구분되지 않습니다.** 실측 결과 DB 프로세스를 종료해도 포화와
똑같은 `PoolTimedOut` 이 나옵니다 — sqlx 가 기존 커넥션을 회수하고 새 연결 시도가
실패하다가 획득 타임아웃에 걸리기 때문입니다.

| 상황 | `ping()` 오류 | 확립된 커넥션 수 |
|---|---|---|
| 커넥션 전부 점유 (DB 정상) | `PoolTimedOut` | **2** (= max) |
| DB 프로세스 종료 | `PoolTimedOut` | **0** |

그래서 판별자는 **확립된 커넥션 수**입니다. 하나라도 있으면 DB 는 응답하고 있다는
뜻이므로 `saturated`, 0 이면 `degraded` 입니다. 오류 종류만 보고 ready 를 유지하면
**완전히 죽은 DB 를 200 으로 보고**하게 되어 readiness 가 영영 실패하지 않습니다 —
이전보다 나쁜 상태이고, 이 릴리스의 첫 구현이 실제로 그랬습니다.

`replicaCount` 가 1 로 고정되므로 **포화만으로 파드를 빼면 부하를 넘길 곳이 없어 열화가
전면 장애로 승격됩니다.** 다중 레플리카라면 부하를 덜어내는 의미가 있지만 여기서는 반대로
작동합니다. 아래 차트의 `readinessProbe` 타이밍 변경과 짝을 이룹니다.

그 사이 해당 `uploadId` 는 `ListMultipartUploads` 에 남고 `UploadPart` 도 받습니다 —

**동작 변경** — 이미지 0.1.18: S3 파트 정리 실패가 이제 오류로 전파됩니다

S3 백엔드의 파트 삭제는 목록 조회 오류를 건너뛰고 개별 삭제 오류를 버린 뒤 **항상
성공을 반환**했습니다. 그래서 아래 GC 수정과 위 abort 수정이 **S3 에서는 아무 효과가

끝까지 지우고, 실패가 하나라도 있으면 오류로 알립니다.

**동작 변경** — 이미지 0.1.18: GC 가 파트 삭제에 실패하면 DB 행을 남깁니다

만료된 멀티파트 업로드를 정리할 때 파트 물리 삭제 오류를 **삼키고 DB 행을 무조건
지우고 있었습니다.** `multipart_uploads` 행이 그 파트가 존재한다는 유일한 기록이므로,
**30초짜리 오브젝트 스토리지 장애가 그 순간 정리 중이던 파트 전부를 영구 잔존으로
바꿨습니다** — 아무 곳에도 기록이 없고 로그도 남지 않았습니다. S3 백엔드에는 기동 시
스윕이 없어(로컬 전용) lifecycle policy 없이는 회수 수단이 없습니다.

이제 실패하면 행을 남겨 다음 GC 패스에서 재시도합니다. 미룬 건수는 `GcResult.errors` 로
나가 `gc_runs` 이력과 `/_api/gc/last-result` 에 드러납니다.

**운영 조치** — S3 백엔드를 쓰신다면 lifecycle 규칙을 두십시오. **프리픽스마다 필요한 규칙
종류가 다릅니다** — `parts/` 의 파트는 네이티브 멀티파트가 아니라 **평범한 객체**라
`AbortIncompleteMultipartUpload` 로는 회수되지 않습니다. 프리픽스별 표와 실효 프리픽스
확인 방법은 README 의 "오브젝트 스토리지 lifecycle 규칙" 절에 있습니다.

**동작 변경** — 유휴 메모리 바닥값을 밀어 올리던 항 하나를 제거했습니다 (이미지 0.1.18)

서버 내부의 해시별 쓰기 락 테이블을 **요청이 끝날 때 즉시 회수**합니다. 이전에는
GC 실행 시에만 회수했기 때문에 **회수 주기가 GC 주기와 같았습니다.** 주기적으로
GC 를 돌리는 배포에서는 그 주기만큼(기본 스케줄이 주 1회이므로 최대 일주일치) 쌓이고,
`gc.enabled: false` 배포(초기 마이그레이션 중 권장 설정)에서는 회수 경로가 아예
없었습니다.

항목은 **고유 해시마다 하나씩** 생기고 항목당 약 180~240바이트입니다. 대량 적재는
고유 해시율이 요청율과 거의 같은 구간이라 증가율이 최대가 됩니다 — 2026-08 운영
사례에서 유휴 바닥값이 4.9일간 **하루 330~430 MiB** 씩 단조 상승했고, 그 기울기를
요청당 비용으로 역산하면 약 234바이트로 위 범위 안에 들어옵니다.

**이것이 관측된 상승분 전부를 설명하는지는 실환경 검증 대기입니다.** 자릿수가 맞고
축소 환경 재현이 실패한 이유까지 설명되지만, 실측으로 확정된 것은 아닙니다.
아래 운영 조치의 완충 유지 항목을 함께 읽으십시오.

`cas_blob_lock_map_entries` 게이지의 **의미가 바뀝니다**:

| 이미지 | 의미 | 유휴 시 기대값 |
|---|---|---|
| 0.1.17 이하 | 누적 고유 해시 수 (GC 시에만 회수) | GC 주기까지 계속 증가 |
| 0.1.18 이상 | 진행 중인 쓰기 건수 | **0** |

0.1.18 이상에서 이 값이 유휴 구간에 0으로 떨어지지 않으면 항목 유출 신호입니다.

GC의 회수 단계를 advisory lock 앞으로 옮겼습니다. 뒤에 있어서 **advisory lock 획득에
실패하거나 DB 오류가 나면** 이 정리까지 함께 건너뛰던 문제가 해소됩니다.
(HTTP 로 GC 를 중복 트리거하는 경우는 핸들러가 `run_gc` 호출 전에 409 를 돌려주므로
원래 회수 단계에 도달하지 않습니다 — 그쪽은 이 이동으로 달라지지 않습니다.)

**동작 변경** — 롤아웃 전략이 `Recreate` 가 됩니다 (짧은 중단이 생깁니다)

지금까지는 `strategy` 를 지정하지 않아 쿠버네티스 기본값 `RollingUpdate` 가 적용됐고,
`replicas: 1` 에서도 `maxSurge = 1` 이라 **모든 업그레이드와 `rollout restart` 에서
구·신 파드가 동시에 Ready 상태로 겹쳤습니다.** 그 창에서 두 프로세스가 서로 다른
per-hash 뮤텍스 맵을 잡습니다 — 차트가 `replicaCount: 1` 을 강제하는 근거가 바로 그
맵의 공유인데, 롤아웃마다 그 근거가 깨지고 있었습니다. GC 가 다른 파드에서 커밋
직전인 blob 을 참조 없음으로 오판해 물리 삭제할 수 있습니다.

**이번 업그레이드부터 롤아웃 중 짧은 중단이 생깁니다.** `replicaCount: 1` 이라 노드
재기동만으로도 어차피 생기는 중단이고, durability 를 그 대가로 사는 편이 낫다고
판단했습니다. 무중단이 더 중요하면 `updateStrategy.type: RollingUpdate` 로 되돌릴 수
있으나, 위 겹침 위험을 감수하는 결정이므로 기록으로 남기십시오.

**설정 키** — `updateStrategy` (기본값 `{type: Recreate}`)

**설정 키** — `config.gcStatementTimeoutSecs` (기본값 `0` = 걸지 않음, **이미지 0.1.18 이상**)

GC 전용 DB 풀에만 `statement_timeout` 을 겁니다. **기본값이 0 이라 설정하지 않으면
동작이 바뀌지 않습니다.**

이 값만이 **PostgreSQL 이 실제로 문장을 취소**하게 합니다. `config.requestTimeoutSecs` 와
`config.dbAcquireTimeoutSecs` 는 "기다리기를 포기"하는 것이고 쿼리는 DB 에서 계속 돕니다.
실행 계획이 틀어져 임시 파일을 대량으로 뱉기 시작하면 애플리케이션 재시작으로도 끊지
못하고 `pg_terminate_backend()` 를 직접 쏘아야 합니다.

**요청 경로 풀에는 적용되지 않습니다.** 대용량 업로드의 메타데이터 커밋을 죽이면 정상
업로드가 실패합니다. GC 는 배치라 잘려도 다음 주기에 재시도하고, 잘린 **실제** 실행은 `gc_runs` 에
`status=failed` 로 남습니다(집계값이 0으로 기록되어 부분 진행분은 이력에 보이지 않습니다).
**`dry_run=true` 실행은 성공·실패 어느 쪽도 `gc_runs` 에 남지 않고 파드 로그에만 남습니다.**

**값을 고정 배수로 두지 마십시오.** 2026-08 운영 건에서 GC 소요가 4초 → 34초 → 94초로
주당 약 3배씩 늘었습니다. 어떤 배수도 몇 주면 소진되고, 정상 실행을 죽이면 GC 가 영구히
완주하지 못합니다. 매주 `gc_runs` 의 소요를 보고 갱신하십시오 — gc-cronjob 의 Job 실행
시간이나 `/_api/gc/last-result` 로 확인할 수 있습니다.

**설정 키** — `config.requestTimeoutSecs` (기본값 `120`)

**기능 추가가 아니라 누락 수정입니다.** 이 차트의 `values.yaml` 주석과 `CHANGELOG` ·
`RELEASE_NOTES` 가 이전부터 이 키를 언급했는데 **ConfigMap 템플릿에는 없었습니다.**
Helm 은 쓰이지 않는 값에 오류를 내지 않으므로, 문서를 따라 `config.requestTimeoutSecs` 를
설정하면 **조용히 무시되고 서버 기본값이 적용됐습니다.** 고쳤다고 믿게 되는 종류의 결함이라
별도로 적습니다.

이 값은 느린 오브젝트 스토리지 백엔드까지 포함한 요청 경로의 유일한 wall-clock 상한입니다.

**설정 키** — `config.statsStatementTimeoutSecs` (기본값 `30`) ·
`config.statsWorkMemMb` (기본값 `0` = 서버 값 사용)

집계 조회 전용 풀의 쿼리 상한과 `work_mem` 입니다. 근거는 위 "집계 조회를 커넥션 1개짜리
별도 풀로 격리" 항목에 있습니다.

`statsWorkMemMb` 는 **PostgreSQL 쪽 메모리**를 씁니다 — 파드 메모리가 아닙니다.
그쪽 사이징을 확인한 뒤 조정하십시오. `0` 이면 건드리지 않습니다.

`statsStatementTimeoutSecs` 는 `with` 가드 없이 항상 렌더됩니다. `0`("타임아웃 없음")이
유효한 선택이고, `with` 는 `0` 을 건너뛰어 서버 기본값 30 이 적용되므로 의도와
반대가 되기 때문입니다.

**설정 키** — `config.dbMinConnections` (기본값 `2`) ·
`config.gcDbMaxConnections` (기본값 `2`) · `config.softDeleteRetentionSecs` (기본값 `604800`) ·
`auth.cacheTtlSecs` (기본값 `10`)

서버에는 있었으나 차트가 렌더하지 않아 **조절할 수 없던 키들입니다.** 모두 서버
기본값과 동일한 값을 넣었으므로 **동작은 바뀌지 않습니다.**

- `dbMinConnections` — 항상 유지할 유휴 커넥션. `0` 이면 트래픽이 뜸한 뒤 첫 요청이
  접속 핸드셰이크 비용을 물습니다(실측 68ms → 정착 후 0.5ms).
- `gcDbMaxConnections` — GC 전용 풀 크기. 파드당 커넥션 총량 계산에 들어갑니다.
- `softDeleteRetentionSecs` — **되돌림 창이 아닙니다.** 아래 주의 항목을 읽으십시오.
- `auth.cacheTtlSecs` — **폐기한 액세스 키나 좁힌 정책이 실제로 막히기까지의 지연**입니다.
  유출 대응 중이라면 `0` 으로 내려 캐시를 끄십시오(요청마다 DB 조회가 늘어납니다).

**동작 변경** — 차트: `storage.mode` 가 잘못되면 렌더 시점에 실패합니다

지금까지 세 경우가 **백엔드 0개로 조용히 렌더**됐고, `helm install` 도 성공했으며 파드만
기동 시 panic 했습니다. `replicaCount: 1` + `Recreate` 조합에서 그것은 전면 장애입니다.

| 입력 | 이전 | 이제 |
|---|---|---|
| `storage.mode=nfs`, `backends` 미지정 | `pvc.yaml` 의 nil pointer 오류 | 무엇을 넣어야 하는지 예시와 함께 실패 |
| `storage.mode=foo` (오타) | **백엔드 0개로 성공** → 파드 panic | 렌더 실패 |
| `storage.mode=NFS` (대문자) | **백엔드 0개로 성공** → 파드 panic | 렌더 실패 |

`storage.nfs.backends` 를 `values.yaml` 에 빈 목록으로 선언했습니다(발견성 목적).
빈 목록으로 렌더를 통과시키지는 않습니다 — 템플릿 오류를 CrashLoopBackOff 로 바꾸는 것은
개선이 아닙니다.

**동작 변경** — 차트: `readinessProbe` 타이밍을 `dbAcquireTimeoutSecs` 와 맞췄습니다

`timeoutSeconds` `5` → `12`, `periodSeconds` `10` → `15`.

`/_internal/health` 는 DB 커넥션을 얻지 못하면 `config.dbAcquireTimeoutSecs`(기본 10)만큼
붙들려 있습니다. `5 < 10` 이었으므로 **서버가 판정을 내리기 전에 프로브가 먼저 끊겼습니다.**
이전 주석은 "프로브 판정 결과는 같다"고 적었는데 **그것이 틀렸습니다** — 판정은 같아도
원인이 다릅니다. 위 readiness 항목의 "포화"와 "단절" 구분을 프로브가 실제로 받으려면
서버가 응답할 시간을 줘야 합니다.

`dbAcquireTimeoutSecs` 를 올리시면 이 값도 함께 올리십시오.

**주의** — `config.maxConcurrentUploads` 와 `dbMaxConnections` 의 대소 관계는 **판정 보류입니다.**

기본값이 `96` 과 `20` 이라 "리미터가 풀보다 위에 있어 동작하지 않는다"고 읽힐 수 있습니다.
**커넥션이 요청당이 아니라 쿼리당 잡히는 것은 맞습니다** — 업로드는 백엔드에 물리 쓰기를
하는 동안 커넥션을 쥐지 않습니다. 다만 그것만으로 두 값이 무관하다고 단정할 수는 없습니다.
메타데이터 커밋의 점유 시간에는 상한이 없고(요청 경로 풀에는 `statement_timeout` 을 걸지
않습니다), `96` 에 닿은 관측도 아직 없습니다.

판정에는 적재 중 `cas_upload_in_flight` 와 `cas_db_pool_idle_connections` 의 동시 표본이
필요합니다. `in_flight` 가 `96` 에 훨씬 못 미치는데 `idle` 이 `0` 으로 지속되면 커넥션이 먼저
소진되는 것이므로, 리미터를 내리는 것이 아니라 `dbMaxConnections` 를 올리는 쪽이 맞습니다.

관련해 `cas_upload_rejected_total` 의 의미를 문서에 명시했습니다. 이 카운터는 건수 상한과
바이트 예산의 거절을 **함께** 셉니다. `0` 이면 둘 다 한 번도 걸리지 않았다는 뜻이고,
어느 쪽이 걸렸는지는 구분할 수 없습니다.

**주의** — `config.softDeleteRetentionSecs` 는 실수 삭제의 되돌림 창이 **아닙니다.**

이 값은 soft-delete 된 `object_versions` **행**의 DB 보존 기간이고 **blob 물리 삭제와
무관합니다.** 삭제가 커밋되는 즉시 blob 은 orphan 후보가 되어 **다음 GC 실행에서 물리
삭제되고**, 그때 그 해시의 soft-delete 행도 함께 지워집니다. 이 값이 실제로 관장하는 것은
그때 치우지 못한 행뿐이라(delete marker, blob 이 아직 살아 있는 행) 용도는 테이블 팽창
관리입니다.

**되돌림 창은 다음 GC 실행까지입니다.** 이 값을 올려도 늘지 않습니다. 실수로 지운 직후라면
아직 살릴 수 있으므로 **다음 GC 를 막으십시오**(`gc.enabled: false`) — 이미 실행 중인 GC 는
멈출 수 없습니다(트리거는 202 를 즉시 반환하고 서버 백그라운드에서 계속 돕니다). 되살리는
작업은 DB 를 직접 고쳐야 하므로 지원팀에 문의하십시오. 자세한 성격과 한계는 README 의
"삭제와 되돌림 창" 절에 있습니다.

**동작 변경** — 차트: `serviceAccount` 블록이 실제로 배선됩니다

지금까지 `values.yaml` 에 이 블록이 있었으나 **어떤 템플릿도 참조하지 않아 설정해도
아무 일도 일어나지 않았습니다.** ServiceAccount 를 만들지도, 파드에 지정하지도
않았습니다. 보안 인접 노브에서 가장 나쁜 실패 형태입니다.

- `create: true` 면 차트가 ServiceAccount 를 만듭니다(`name` 이 비면 fullname).
  `false` 면 기존 것을 쓰고, `name` 도 비면 네임스페이스의 `default` 입니다.
- **Deployment 와 GC CronJob 양쪽**에 지정됩니다. 한쪽만 하면 두 워크로드가 서로 다른
  신원으로 돌아 IRSA/Workload Identity 애노테이션이 한쪽에만 걸립니다.
- `serviceAccount.automountToken` 은 **기본 `false`** 입니다. 이 서버는 쿠버네티스 API 를
  부르지 않는데, 마운트된 토큰은 컨테이너가 뚫렸을 때 그대로 API 접근 수단이 됩니다.
  이 배포는 `auth.anonymousGet` 이 기본 `true` 이고 NodePort 로 노출되므로 표면을
  늘리지 않는 편이 낫습니다.
- `serviceAccount.annotations` 를 추가했습니다. AWS IRSA · GCP Workload Identity 설정 자리입니다.

기본값(`create: false`, `name: ""`)에서는 지금까지처럼 `default` SA 로 돕니다.
다만 `automountToken: false` 가 파드에 걸리므로 **`default` SA 의 토큰 자동 마운트는
이번 릴리스부터 막힙니다.** 사이드카 등으로 쿠버네티스 API 를 쓰고 계셨다면
`serviceAccount.automountToken: true` 로 되돌리십시오.

**설정 키** — `auth.metricsToken` (기본값 `""`)

`GET /_internal/metrics` 전용 **읽기 전용** Bearer 토큰입니다. 지금까지 이 엔드포인트는
`admin_token` 을 요구했고, 그 토큰은 `POST /_internal/gc`(blob 물리 삭제)와
`/_admin/*`(액세스 키 관리)까지 여는 자격증명입니다. 스크레이프를 붙이려면 삭제 권한을
모니터링 스택에 배포하거나 메트릭을 포기하거나 둘 중 하나를 골라야 했습니다.

- 비워 두면 `admin_token` 으로 폴백합니다 — **기존 배포의 동작이 바뀌지 않습니다.**
- `admin_token` 은 계속 메트릭을 읽을 수 있습니다. 업그레이드가 스크레이프를 끊지 않습니다.
- `metricsToken` 은 metrics 엔드포인트에서만 통합니다. GC 도 admin API 도 열지 않습니다.
- **`metricsToken` 만 채우고 `adminToken` 을 비우면 서버가 기동을 거부합니다.**
  그 조합에서는 metrics 만 잠기고 `POST /_internal/gc`(blob 물리 삭제)가 무인증으로
  열려, 401 을 보고 보호된다고 오해하게 되기 때문입니다. `replicaCount: 1` 이라
  기동 실패는 곧 전면 중단이므로, 둘을 함께 설정하거나 `metricsToken` 을 비워 두십시오.

**운영 조치** — Secret 을 갱신했으면 파드를 직접 재시작하십시오.

`secrets.useExternalSecret: true`(기본값)에서는 Helm 이 Secret 내용을 볼 수 없어
체크섬을 걸 수 없습니다. `kubectl apply -f sealed-secret.yaml` 만으로는 파드가
교체되지 않고, env 는 파드 생성 시점에 주입되므로 새 토큰이 반영되지 않습니다.
그 상태에서 모니터링을 새 토큰으로 바꾸면 스크레이프가 401 이 되고 원인이
"토큰이 틀렸나"로 보입니다.

```bash
kubectl rollout restart -n <namespace> deploy/cas-server
```

업그레이드와 함께 갱신한다면 **Secret 을 먼저 적용**하고 `helm upgrade` 하면 파드
교체와 함께 들어갑니다. (차트가 Secret 을 만드는 `useExternalSecret: false` 배포에는
이번 릴리스에서 `checksum/secret` 애노테이션을 추가해 자동 재시작됩니다.)

**운영 조치** — 모니터링 스택에 admin 토큰을 배포해 두셨다면 이 토큰으로 교체하십시오.

`secrets.useExternalSecret: true`(기본값)면 sealed-secret 에 `auth-metrics-token` 키를
추가합니다. 이 키는 **선택 항목**이고, deployment 에서 `optional: true` 로 참조하므로
키를 추가하지 않아도 파드는 정상 기동합니다. 기존 7개 키 Secret 그대로
업그레이드하셔도 됩니다.

```bash
kubectl create secret generic cas-server   --namespace=<namespace>   --from-literal=db-password='...'   --from-literal=s3-access-key-id='...'   --from-literal=s3-secret-access-key='...'   --from-literal=auth-secret-master-key='...'   --from-literal=auth-admin-token='...'   --from-literal=auth-metrics-token='...'   --from-literal=auth-root-access-key-id='...'   --from-literal=auth-root-secret-key='...'   --dry-run=client -o yaml > /tmp/secret-plain.yaml
kubeseal --format yaml < /tmp/secret-plain.yaml > sealed-secret.yaml && rm /tmp/secret-plain.yaml
```

**주의** — `gc.enabled: false` 와 메모리의 관계를 이번에 처음 문서화했습니다.

**이미지 0.1.17 이하**에서 GC 를 끄면 위 락 테이블의 회수 경로도 함께 사라집니다.
그 이미지로 GC 를 끈 채 대량 적재해야 한다면, 적재 기간에
`POST /_internal/gc?dry_run=true`(admin 토큰 필요)를 주기 실행해 완화하십시오 —
blob 물리 삭제도 advisory lock 도 없이 그 테이블을 회수합니다. 함께 도는 것은
읽기 전용 쿼리 두 개(orphan 후보 COUNT, 만료 멀티파트 목록)이고, 회수 자체는
샤드를 하나씩 잠그고 지나가므로 쓰기 경로 전체를 멈추지는 않습니다.
**주기를 정하기 전에 한 번 수동으로 돌려 소요 시간을 재십시오.**

**주의** — 0.1.23 에서 신설한 **"롤백 안전" 규칙이 틀렸습니다. 이 파일 위쪽의

**동작 변경** — 이미지 0.1.17: 설정 오류 시 기동 실패 방식

  ```
  ERROR cas_server: 설정 로드 실패: missing field `admin_token`
    → `admin_token`은 [auth] 섹션의 필수 항목입니다. config/default.toml의 [auth]에 추가하세요.
  ```

- 부수 효과로 원인 로그가 사라지지 않습니다. 종전에는 원인을 알려주는 WARN이 기동 시

**동작 변경** — 차트

- `startupProbe` 추가 (`startupProbe.enabled: true`, 기본 예산 600초).

  liveness 예산을 넘겨 파드가 kill되던 문제를 해소합니다 — 0.1.16 최초 배포에서

- `livenessProbe` 대상이 `/_internal/health` → `/_internal/live` 로 바뀝니다.
  종전에는 liveness가 DB와 blob 백엔드 가용성까지 확인해서, DB failover나 NAS
  순간 장애에 파드가 죽었습니다. 재시작으로는 외부 의존성이 복구되지 않으므로

- `livenessProbe`/`readinessProbe` 의 `timeoutSeconds` 가 실제로 적용됩니다.
  종전 템플릿이 이 필드를 렌더링하지 않아 values의 `5` 가 무시되고 쿠버네티스
  기본값 **1초**가 적용되고 있었습니다. 프로브가 설정보다 훨씬 쉽게 실패하던
  상태이므로, 이 값을 조정해 두셨다면 실제 반영 결과를 확인하세요.
- `terminationGracePeriodSeconds` 가 실제로 적용됩니다. 같은 이유로 values의 `60` 이
  무시되고 기본값 **30초**가 적용되고 있었습니다. 종료 유예가 30초에서 60초로 늘어납니다.

**마이그레이션** — 없음 (이미지 0.1.17은 스키마를 바꾸지 않습니다)

**설정 키**

**호환성** — 이 차트는 **이미지 `0.1.16` 이상**을 요구합니다. 아래 `config.*` 세 키를

**동작 변경** — 이미지 0.1.16: 2026-08-05 운영 OOMKilled 반복 수정

`limits.memory: 2Gi` 에서 6일 15시간 동안 12회 OOMKilled 된 사고의 수정입니다.
원인은 셋이고, 기여도 순서는 **③ → ② → ①** 입니다(보고서는 ①→②→③ 으로 보셨으나
재분석 결과 역순이었습니다 — OOM 직전 157초 동안 느린 SQL 이 0건이었습니다).

**③ 할당자가 최고 수위를 OS 에 반환하지 않았습니다 (주 원인)**

`glibc malloc` 은 수 MiB 바디 버퍼를 반복 할당·해제하면 최초 해제 시 mmap 임계값을
그 크기로 **상향**시킵니다. 이후 같은 크기 할당은 arena 힙에서 나오고, 동시 요청이
뒤섞여 해제되면 힙 내부에 갇혀 trim 대상이 되지 못합니다. 결과적으로 부하 최고 수위가
**영구 고착**됩니다 — 유휴 17 MiB 였던 프로세스가 부하 후 1.9 GiB 에서 내려오지 않았고
재시작 없이 회복되지 않았습니다.

전역 할당자를 **jemalloc 5.3.0** 으로 교체하고 `background_thread:true` 를 켰습니다.
decay 는 할당 활동이 있어야 진행되므로, 적재가 끝나 유휴가 된 프로세스에서도 반환되려면
이 설정이 필수입니다. `dirty_decay_ms` / `muzzy_decay_ms` 는 10초로 명시했습니다.

**② 요청당 바디를 객체 크기의 2배로 보유했습니다 (수위 결정)**

- 인라인 경로가 수신 청크를 **연속 버퍼로 이어붙이지 않습니다.** 청크를 그대로 보관하며
  해시를 계산합니다(BLAKE3 는 스트리밍 계산이라 연속 메모리가 불필요). 요청당 memcpy 와
  객체 크기만 한 연속 블록 할당이 함께 사라졌습니다 — 후자가 ③ 의 먹이였습니다.
- S3 계층의 **재복사를 제거**했습니다(4개 경로). 요청당 순간 점유가 2배 → 1배입니다.
- **dedup 히트 시 메타데이터 커밋 전에 바디를 해제**합니다.
- 스트리밍 경로의 요청당 상한을 파트 하나 분량(5 MiB)으로 낮췄습니다.

**남은 한계**: dedup 미스 경로는 여전히 바디를 든 채로 DB 왕복 2회(백엔드 조회,
blob 존재 확인)를 통과합니다. 풀이 포화되면 그 구간이 `db_acquire_timeout_secs` 까지
늘어날 수 있습니다.

**① `buckets` 단일 행 잠금 컨보이 (이번 OOM 의 인과에는 미포함)**

PUT 마다 `buckets` 의 같은 행에 `ON CONFLICT DO UPDATE` 를 실행해, 커넥션 풀 20개 중
18개가 한 문장에 묶이는 구간이 있었습니다. `ON CONFLICT (name) DO NOTHING` + 별도
`SELECT versioning` 으로 분리했습니다. `DO NOTHING` 은 이미 커밋된 충돌 행을 잠그지
않고 건너뜁니다.

대가로 메타데이터 트랜잭션의 DB 왕복이 1회 → **2회**가 됩니다. 추가분은 PK 인덱스
단건 SELECT 이고 61 PUT/s 기준 커넥션 점유 증가는 약 0.09% 입니다.
(프로세스 내 버킷 캐시는 도입하지 않았습니다 — `PutBucketVersioning` 변경이 TTL 만큼
지연되는 staleness 를 새로 들여오기 때문입니다.)

**동작 변경** — 이미지 0.1.16: 동시 업로드 상한 신설

두 축이고 **기본값이 둘 다 0(무제한)** 입니다. 새 버전으로 올리는 것만으로는 상한이
걸리지 않습니다 — ConfigMap 에 명시하셔야 합니다.

초과분은 대기시키지 않고 즉시 **`503 SlowDown` + `Retry-After: 1`** 로 거절합니다.
대기시키면 거절 대신 바디를 든 요청이 그대로 쌓여 상한의 목적이 사라집니다.
자리 확보는 **바디를 읽기 전**에 이루어집니다.

**메모리를 제한하려면 바이트 예산(`maxUploadBytesInFlight`)을 쓰십시오.** 건수 상한만으로는
요청당 바디 크기를 클라이언트가 정하므로 메모리가 유계가 되지 않습니다 — 9 MiB 기준으로
산정한 건수는 200 MiB 객체 앞에서 아무 것도 막지 못하고, 그때 지표는 "상한 여유 충분"을
표시합니다. 바이트 예산은 cgroup 한도와 같은 단위라 산정도 직관적입니다.

**주의**: `503` 이 두 의미를 갖게 됩니다 — 백엔드 불가용(기존)과 상한 초과(신규)입니다.
구분은 `cas_upload_rejected_total` 증가로 하십시오.

**동작 변경** — 이미지 0.1.16: GC 와 업로드의 직렬화가 성립하지 않던 결함 수정

**이번 OOM 과는 별개이며 데이터 무결성에 관한 것입니다.**

cas-server 는 같은 콘텐츠에 대한 동시 쓰기를 per-hash 뮤텍스로 직렬화하고, GC 의 orphan
재검증도 같은 뮤텍스를 잡아 "GC 가 진행 중인 업로드의 blob 을 orphan 으로 오판해 삭제하는
것"을 막도록 설계돼 있습니다. 그런데 운영 프로세스에는 스토어 인스턴스가 둘(요청 경로용 /
GC 전용 DB 풀)이고 **뮤텍스 맵이 인스턴스마다 별도로 생성되어 서로 다른 락을 잡고
있었습니다.** 즉 그 방어가 동작하지 않았습니다.

영향은 "GC 실행 중에 같은 콘텐츠의 업로드가 겹치면 메타데이터에는 객체가 있는데 실물이
없는 참조가 생길 수 있음"입니다. 조건은 (a) 해당 blob 의 참조가 모두 사라져 있고
(b) 바로 그 시점에 같은 콘텐츠가 업로드될 때로 제한됩니다.

GC 인스턴스를 요청 경로 인스턴스에서 파생시켜 맵을 공유하도록 바꾸고, 공유되지 않으면
**기동 시점에 중단**하는 가드를 넣었습니다.

**동작 변경** — 이미지 0.1.16: `/_internal/metrics` 에 지표 8종 추가

| 지표 | 종류 | 의미 |
|---|---|---|
| `cas_upload_in_flight` | gauge | 현재 인플라이트 업로드 건수 |
| `cas_upload_in_flight_bytes` | gauge | 인플라이트 업로드가 예약한 바디 바이트. 바이트 예산의 판정 기준 |
| `cas_upload_limit` | gauge | 설정된 건수 상한 (0 = 무제한) |
| `cas_upload_rejected_total` | counter | 상한 초과로 거절한 누적 건수 |
| `cas_blob_lock_map_entries` | gauge | per-hash 뮤텍스 맵 항목 수 |
| `cas_db_pool_connections` | gauge | DB 커넥션 풀의 **현재** 커넥션 수 (max 가 아님) |
| `cas_db_pool_idle_connections` | gauge | 유휴 커넥션 수 (현재 − 유휴 = 사용 중) |
| `cas_db_pool_acquire_timeouts_total` | counter | 풀 획득 타임아웃 누적 (HTTP 응답이 된 것만) |

"커넥션 획득을 **대기 중**인 요청 수"는 sqlx 가 노출하지 않아 제공하지 못합니다.
`connections − idle_connections = 사용 중` 으로 포화를 판단하고
`cas_db_pool_acquire_timeouts_total` 증가를 함께 보십시오.

`/_internal/health` 의 `db: true` 는 ping 성공만 의미하고 풀 포화를 반영하지 않습니다.
이 지표만으로 정상 판정하지 마십시오.

**설정 키** — 추가 3개 (모두 이미지 0.1.16 이상 필요)

| 키 | 기본값 | 의미 |
|---|---|---|
| `config.maxUploadBytesInFlight` | `0` (무제한) | 인플라이트 업로드가 점유할 수 있는 바디 바이트 총합. **`limits.memory` × 0.5 를 기준으로 함께 조정할 것** |
| `config.maxConcurrentUploads` | `0` (무제한) | 동시 업로드 건수. 위 바이트 예산의 보조 장치 |
| `config.inlineHashLimitBytes` | `268435456` (256 MiB) | 이 값 이하이면 메모리 버퍼링으로 해시 계산, 초과하면 스트리밍 경로. **낮출 필요가 없습니다** — 요청당 상한을 두려는 목적이면 `maxUploadBytesInFlight` 를 쓰는 것이 맞습니다 |

**운영 조치** — 임시 조치 환경변수를 제거하십시오.

`MALLOC_ARENA_MAX` / `MALLOC_MMAP_THRESHOLD_` / `MALLOC_TRIM_THRESHOLD_` 를
`extraEnv` 로 넣어 두셨다면 지우십시오. 이 이미지는 glibc malloc 을 쓰지 않으므로
효과가 없고, 남겨 두면 나중에 원인 분석을 흐립니다.

**운영 조치** — 상한 두 개를 ConfigMap 에 명시하십시오. 기본값이 0(무제한)이라
올리는 것만으로는 걸리지 않습니다.

**마이그레이션** — 이 버전 자체는 스키마를 바꾸지 않습니다.
